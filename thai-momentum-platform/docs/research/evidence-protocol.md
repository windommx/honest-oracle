# โปรโตคอลหลักฐาน (Evidence Protocol) — วิธีได้คะแนนหลักฐานอย่างซื่อตรง

> สถานะ ณ 23 ก.ย. 2026: **ยังไม่มีหลักฐานว่ากลยุทธ์มี edge บนข้อมูล SET จริง** — ตัวเลขทุกตัวในแพลตฟอร์มมาจากข้อมูลจำลอง (demo seed)
> หรือชุดทดสอบ (fixture) และยังไม่มี track record แบบ live/out-of-sample
> เอกสารนี้กำหนด "ขั้นตอนตายตัว" ที่ต้องทำก่อนจะอ้างว่ามี (หรือไม่มี) edge — ทำตามลำดับ ห้ามข้ามขั้น ห้ามย้อนแก้

หลักการเดียว: **หลักฐาน = ผลที่ได้จากกติกาที่ล็อกไว้ก่อนเห็นผล บนข้อมูลจริง ที่ใครก็ตรวจย้อนได้**
ผล backtest ที่ดูดีบนข้อมูลที่เคยเห็นแล้วไม่ใช่หลักฐาน · ผลที่ออกมา "ไม่มี edge" คือผลลัพธ์ที่มีค่าเท่ากัน และต้องเผยแพร่เหมือนกัน

## ขั้นที่ 0 — เครื่องมือที่ใช้ (มีครบในแพลตฟอร์มแล้ว)

| เครื่องมือ | ทำอะไร | ป้องกันอะไร |
|---|---|---|
| `GET /api/data/trust` · แท็บ Track Record (TR5) | ที่มา/สิทธิ์การใช้ของแต่ละแหล่ง · ความสดเทียบปฏิทิน SET · reconciliation · corporate action | ใช้ข้อมูลผิดแหล่ง/ค้าง/ยังไม่ปรับปันผลโดยไม่รู้ตัว |
| `bun run evidence:real` → `data/reports/evidence-YYYY-MM-DD.json` | Evidence Board H1–H4 + Signals IC + walk-forward บน DB ปัจจุบัน · ไม่เขียน config/policy | ติดป้าย REAL ให้ข้อมูลจำลอง/ประวัติสั้น (สคริปต์ปฏิเสธเอง) |
| `/api/research/prereg` (freeze) | ล็อกกติกาการทดลองด้วย sha256 ก่อนเห็นผล | ปรับพารามิเตอร์หลังเห็นผล (curve fitting) |
| `bun run daily` (cron หลังตลาดปิด) | ดึงข้อมูล → ตรวจ → สมอง Jev → verify → track snapshot → backup → run log | ข้อมูลเสียเข้าสมอง · วันที่ขาดหาย · แก้ประวัติย้อนหลัง |
| `GET /api/track-record` · แท็บ Track Record | NAV รายวัน vs benchmark (ไม้เข้าที่ราคาปิดวันเติม T+1 — คำสั่งที่ยังรอเติมไม่นับ · methodology A5) · สถิติ · ป้าย SYNTHETIC/REAL · LIVE/REPLAY · ความเชื่อมั่น · audit hash | อ้างผลงานเกินจริง (รวมราคาเข้าที่ซื้อไม่ได้จริงหลังเห็นสัญญาณ EOD) · เลือกช่วงเวลาที่ดูดี |
| EventLog hash chain (`/api/events/audit`) + ledger hash + track snapshot | ทุกเหตุการณ์ผูกด้วย sha256 · snapshot รายวันเก็บ ledger hash + NAV | แก้ Decision/ราคาย้อนหลังเงียบ ๆ |

## ขั้นที่ 1 — นำเข้าข้อมูล SET จริง ≥ 5 ปี (ทำครั้งเดียว บนเครื่องที่เข้าเน็ตได้)

1. **เลือกแหล่งหลักแหล่งเดียวสำหรับประวัติทั้งชุด** (อย่าผสมราคาดิบกับราคาปรับปันผล):
   - เริ่มต้นเร็วสุด: Yahoo (.BK, ราคาปรับแล้ว) — `bun run fetch:th -- --symbols CORE --range 5y --replace-demo`
   - มูลค่าซื้อขายจริง: settfex — `python lab/fetch_set_feed.py --index SET100 --period 5Y --ohlc-from-yahoo --post http://localhost:3000 --replace-demo`
   - ทางการ: Settrade Open API (ต้องมีบัญชีโบรกเกอร์) — `lab/fetch_settrade_feed.py`
   - `--replace-demo` ใช้ **ครั้งเดียวตอนเริ่ม** (ระบบ backup + ขอ confirm ให้) — การล้างข้อมูลทั้งชุดครั้งถัดไปจะ **เริ่มยุคข้อมูลใหม่ และ track record นับใหม่จากศูนย์** (การตัดสินใจเก่าถูกแยกเป็น "ก่อนยุคนี้")
2. `bun run fetch:cross` — SPX/USDTHB/GOLD จริง (ไม่งั้น crossZ ปิด)
3. **ตรวจที่แท็บ Track Record → TR5 / `GET /api/data/trust`:**
   - ป้ายต้องเป็น `REAL` (ไม่ใช่ `SYNTHETIC` / `MIXED` / `UNVERIFIED_SOURCE`)
   - freshness = สด · อัปเดต ≥ 80% ของ universe · corporate action ที่ติดธงตรวจกับประกาศ SET ครบทุกจุด
   - DQ (`/api/dq`) ไม่มีช่องว่างวันที่ผิดปกติ
4. **บันทึกข้อจำกัดของชุดข้อมูลตามจริง** (ต้องเขียนไว้ในรายงาน ห้ามซ่อน):
   - **Survivorship bias:** รายชื่อใน `src/lib/feed/universe.ts` เป็นองค์ประกอบดัชนีปี 2026 และ Yahoo ไม่มีหุ้นที่ถูกเพิกถอนไปแล้ว — backtest 5 ปีบนรายชื่อปัจจุบันจึง "เลือกผู้รอด" ผลย้อนหลังดีเกินจริง
     ทางแก้ที่ดีกว่า: ประวัติจาก SETSMART/Settrade ที่รวมหุ้นเพิกถอน และองค์ประกอบดัชนี ณ แต่ละช่วงเวลา
   - Yahoo: val = close×volume โดยประมาณ · ข้อกำหนดการใช้ = ส่วนตัว ไม่ใช่เชิงพาณิชย์
   - ปฏิทินวันหยุดในโค้ด (`src/lib/feed/calendar.ts`) เป็น best-effort — ตรวจกับประกาศวันหยุดของ SET ทุกปีแล้ววางไฟล์ `SET_HOLIDAYS_FILE`

## ขั้นที่ 2 — รายงานหลักฐานบนข้อมูลจริง (in-sample)

```bash
bun run evidence:real            # → data/reports/evidence-YYYY-MM-DD.json + EventLog "evidence_real" (hash ของรายงาน)
```

- สคริปต์ **ติดป้าย REAL ได้เฉพาะ** ข้อมูลจริงล้วนจากแหล่งที่รู้จัก **และ** ประวัติ ≥ 250 วันซื้อขาย — ไม่งั้นทุก verdict เป็น `NOT_REAL` (`countsAsEvidence: false`)
- รายงานเก็บ `dataFingerprint` + `paramsHash` ของทั้ง 3 ชุดทดสอบ → ใครรันซ้ำบนข้อมูลเดียวกันต้องได้ผลเดียวกัน
- อ่านผลตามตารางใน **"อะไรนับว่าไม่มี edge"** ด้านล่าง — **ผลขั้นนี้เป็นเพียงเงื่อนไขจำเป็น** (in-sample + survivorship) ไม่ใช่หลักฐานพอ
- ถ้าขั้นนี้ออกมา "ไม่มี edge" ชัดเจน: หยุดที่นี่ เผยแพร่รายงาน แล้วกลับไปออกแบบสมมติฐานใหม่ (นับเป็น trial ใหม่) — **ห้ามจูนพารามิเตอร์จนกว่าจะผ่าน**

## ขั้นที่ 3 — ล็อกกติกาล่วงหน้า (pre-registration + live freeze) ก่อนเริ่มนับ live

1. เขียนสมมติฐานหลัก **ข้อเดียว** และตัวชี้วัดหลัก **ตัวเดียว** ก่อนเริ่ม เช่น
   > "พอร์ตกระดาษ Jev (กติกาปัจจุบัน + config_th ณ วันที่ล็อก) ให้ผลตอบแทนส่วนเกินรายวันเหนือ benchmark equal-weight หุ้นสภาพคล่อง หลังต้นทุน 0.7%/ขา
   > โดย t-stat ≥ 2 เมื่อครบ 120 วันซื้อขาย และ ≥ 30 เทรดที่ปิดแล้ว"
2. ตั้งกติกาให้เสร็จ **ก่อน** ล็อก (ช่วงนี้ยังเปลี่ยนได้): แท็บ Signals (`GET /api/signals/ic?hold=<ค่าที่จะใช้>` เขียน `signals_policy`) · แท็บ Stops
   (`GET /api/stops` เขียน `stops_policy`) · `config_th` (แท็บ Evidence / `PUT /api/config/th`) · CPCV deploy `meta_model` ถ้าจะใช้ ·
   `POST /api/research/prereg` (กติกา trial) — จด `hash` + `frozenAt`
3. **ล็อกช่วงเก็บผลจริง:** แท็บ Evidence → การ์ด "ล็อกช่วงเก็บผลจริง" (ใส่สมมติฐานจากข้อ 1 เป็นบันทึก) หรือ
   ```bash
   curl -X POST -H "Authorization: Bearer $TMP_API_TOKEN" -H "Content-Type: application/json" \
     -d '{"action":"freeze","note":"<สมมติฐานหลัก + ตัวชี้วัดหลัก>"}' http://127.0.0.1:3000/api/research/freeze
   ```
   ระบบเก็บ sha256 ของค่าดิบใน Setting ที่ Jev อ่านเป็นกติกา (`config_th` · `signals_policy` · `stops_policy` · `meta_model` · `prereg_trial`)
   + วันที่ข้อมูลล่าสุด + prereg hash ลง `Setting.live_freeze` และ EventLog `live_freeze` (hash chain) — ล็อกอยู่แล้วล็อกซ้ำ = 409
4. **เผยแพร่** ผลของ `GET /api/research/freeze` (`freeze.frozenAt` · `freeze.hashes` · `freeze.preregHash` · `freeze.note`) พร้อมค่าจริงของแต่ละ Setting
   แล้ว commit/โพสต์ในที่ที่แก้ย้อนหลังไม่ได้ — ใครมีสำเนา DB ตรวจ hash ได้เอง:
   `printf '%s' "$(sqlite3 app.db "select value from Setting where key='config_th'")" | sha256sum`
5. **ระหว่างล็อก ระบบกันการเปลี่ยนกติกาเอง** (ไม่ต้องจำว่าห้ามกดอะไร):
   - `GET /api/signals/ic` และ `GET /api/stops` **เปิดได้ปลอดภัย** — คำนวณและแสดงผลตามปกติแต่ไม่บันทึก policy/Decision/event
     (`policySaved:false` · `adoption.saved:false` · `frozen:true` + ป้าย "🔒 ล็อกช่วงเก็บผลจริง") · Jev อ่าน policy ที่ล็อกไว้ต่อ
   - `POST /api/evidence/run` รันแบบอ่านอย่างเดียว (บันทึก ResearchRun — นับเป็น trial — แต่ไม่ auto-apply `config_th`) · `PUT /api/config/th` → 409
   - ค่าที่ถูกแก้ข้ามด่าน (แก้ตรงใน DB · deploy `meta_model` · reset prereg · seed/`--replace-demo` ที่ล้าง policy) → **drift** ขึ้นป้ายแดงที่แท็บ Evidence /
     Signals / Stops / Track Record และใน `GET /api/research/freeze` · บันทึกล็อกที่ถูกแก้/ลบตรงใน DB ไม่ตรงกับ EventLog → ขึ้นป้ายแดงเช่นกัน
6. ถ้าจำเป็นต้องเปลี่ยนกติกา → **ถือเป็น trial ใหม่**: ปลดล็อก (แท็บ Evidence ต้องพิมพ์ `UNFREEZE` + เหตุผล หรือ
   `{"action":"unfreeze","confirm":"UNFREEZE","reason":"…"}` — เหตุผลและ drift ที่พบลง EventLog) → เปลี่ยน → ล็อกใหม่ → เริ่มนับใหม่
   และรายงานทั้งสอง trial (ห้ามทิ้ง trial ที่แพ้)

## ขั้นที่ 4 — Paper trade ทุกวันซื้อขาย อย่างน้อย N เดือน

```cron
30 18 * * 1-5   cd /app && bun run daily >> data/runs/cron.log 2>&1
```

- ขั้นต่ำก่อนตีความ: **60 วันซื้อขาย และ 30 เทรดที่ปิดแล้ว** (แท็บ Track Record แสดง "ยังเร็วเกินไปที่จะตัดสิน" จนกว่าจะครบ)
- แนะนำ: **6–12 เดือน** (120–250 วันซื้อขาย) — edge ของ momentum ไทยขนาดเล็ก ต้องใช้ตัวอย่างมากกว่าที่คิด (`sessionsForSignificance` ในแท็บประมาณจำนวนวันที่ต้องสะสมจาก edge ที่เห็น)
- สายพานรายวันหยุดเองเมื่อข้อมูลไม่ผ่านเกณฑ์ (exit 3/4/5/6) — **แก้แล้วรันซ้ำ (หรือ `--date <วันนั้น>`) ก่อนข้อมูลของวันซื้อขายถัดไปเข้าฐาน** (รันก่อน 17:30 ของวันถัดไป สายพานตามเก็บรอบที่ค้างให้เอง) ไม่งั้นรอบนั้นหายไปถาวร เพราะ Jev ตัดสินใจบนข้อมูลล่าสุดเท่านั้น ไม่ตัดสินใจย้อนหลัง — รอบที่หายต้องรายงานตามจริง
- ป้าย **LIVE/REPLAY**: รอบตัดสินใจที่ช้ากว่าวันของข้อมูลเกิน 4 วันปฏิทิน = REPLAY — นับเป็นหลักฐาน live ไม่ได้
- มนุษย์อนุมัติ/ปฏิเสธ gate ได้ตามปกติ (บันทึกเป็น Decision source=human) — แต่ต้องทำก่อนรอบถัดไป และรายงานแยกได้ (track record นับทุกไม้ที่เข้าจริง)
- ทุกวันที่ผลเปลี่ยน สายพานบันทึก `track_snapshot` (ledger hash + NAV + ขนาดไม้เปิด) ลง EventLog — ทำให้ไม้ที่ปิดภายหลังไม่ต้องประมาณขนาด และตรวจการแก้ย้อนหลังได้
- แท็บ Track Record (TR4 + ป้ายบนหัว) แสดงวันที่ล็อก และขึ้นป้ายแดงเมื่อกติกาไม่ตรงกับที่ล็อก / มีการเปลี่ยนกติกาใน EventLog หลังล็อก (`freeze.violated`) —
  หลักฐานนับเฉพาะรอบตัดสินใจหลังวันล็อก (record ที่เริ่มก่อนล็อกขึ้นหมายเหตุ) · ตรวจการ์ดล็อกที่แท็บ Evidence อย่างน้อยสัปดาห์ละครั้ง

## ขั้นที่ 5 — เผยแพร่ track record พร้อม audit hash

1. ส่งออก `GET /api/track-record` (JSON) + รายงาน `evidence-*.json` ทุกฉบับ (รวมฉบับที่ผลแย่)
2. เผยแพร่พร้อม: `tamper.latestEvent.hash` · `tamper.ledgerHash` · `liveSince` · `provenance` · `mode` · prereg hash · `freeze.frozenAt` + `freeze.hashes` — ใครมีสำเนา DB ตรวจได้ว่า
   - EventLog chain ครบ (`/api/events/audit` → ok) และ hash ล่าสุดตรงกับที่เผยแพร่
   - `tamper.snapshots.ledgerMismatches = 0` (ประวัติการตัดสินใจไม่ถูกแก้หลังบันทึก) · `navMismatches = 0` (ราคาไม่ถูกแก้ย้อนหลัง)
   - `freeze.violated = false` และ `freeze.hashes` ตรงกับที่เผยแพร่ตอนล็อก (กติกาชุดเดียวตลอดช่วงที่นับ)
3. เผยแพร่ hash เป็นระยะ (เช่นทุกสัปดาห์) ในที่ที่แก้ย้อนหลังไม่ได้ (git commit / โพสต์สาธารณะ) — hash ที่เผยแพร่ก่อนเป็นเครื่องยืนยันว่าไม่ได้สร้าง track record ขึ้นทีหลัง

## อะไรนับว่า "ไม่มี edge" (ตัดสินล่วงหน้า — ไม่ต่อรองหลังเห็นผล)

| ระดับ | เงื่อนไข (อย่างใดอย่างหนึ่ง) | ข้อสรุป |
|---|---|---|
| in-sample (ขั้น 2) | walk-forward: Sharpe นอกตัวอย่าง (มัธยฐาน) ≤ 0 **หรือ** เสื่อมจาก IS > 50% | การเลือกพารามิเตอร์ fit อดีต — ใช้ config ที่ลงทะเบียนล่วงหน้าเท่านั้น |
| in-sample | Signals IC: ไม่มีสัญญาณใด PROMOTE (\|IC\| > 0.02, \|ICIR\| > 0.25, n ≥ 120, เครื่องหมายตรง) | ชั้น alpha ไม่มีฐาน — เหลือเพียงตัวกรองความเสี่ยง |
| in-sample | H1 FAIL (ไม่มี cell สายสั้น ICIR > 0.25) | โมเมนตัมระยะสั้นไม่มีหลักฐานในข้อมูลชุดนี้ |
| live (ขั้น 4) | ครบ 60 วัน + 30 เทรดแล้ว t-stat ส่วนเกิน benchmark < 2 | **ยังไม่มีหลักฐาน** (NO_EDGE_YET) — สะสมต่อได้แต่ห้ามเปลี่ยนกติกา |
| live | t-stat ≤ −2 | **แพ้ benchmark อย่างมีนัยสำคัญ** (UNDERPERFORM) — หยุด ทบทวน |
| live | ส่วนเกินรวมติดลบหลังต้นทุน **หรือ** hit rate < 50% พร้อม payoff < 1 | ไม่มี edge หลังต้นทุน |
| live | ผลบวกมาจากหุ้นตัวเดียว/ช่วงสั้นช่วงเดียว (ตัดไม้ที่ดีที่สุด 1 ไม้แล้วส่วนเกินหายไป) | ผลไม่ robust — ยังไม่ใช่ edge |

ป้ายสูงสุดที่แพลตฟอร์มให้คือ **PROMISING** (t ≥ 2 บนข้อมูลจริง ครบเกณฑ์ขั้นต่ำ) — ไม่มีป้าย "พิสูจน์แล้ว"
การอ้างว่ามี edge ต้องเห็น PROMISING ต่อเนื่องหลายเดือน บนกติกาที่ล็อกไว้ และทนต่อ trial อื่นที่เคยทดสอบ (ดูข้อ p-hacking)

## วิธีกัน p-hacking

1. **หนึ่งสมมติฐานหลัก หนึ่งตัวชี้วัดหลัก** ล็อกก่อนเริ่ม — ตัวชี้วัดอื่น (Sharpe, hit rate, drawdown) เป็นข้อมูลประกอบ ไม่ใช่ทางหนีเมื่อตัวหลักแพ้
2. **นับทุก trial:** ทุกการรัน Evidence/Trial/CPCV ถูกบันทึกใน `ResearchRun` และ EventLog อยู่แล้ว — รายงานจำนวน trial ทั้งหมดคู่กับผลที่ดีที่สุดเสมอ
   ยิ่งทดลองหลายแบบ เกณฑ์ต้องยิ่งเข้ม (Bonferroni: t ≥ ~2.5 เมื่อทดสอบ 5 แบบ · ~3 เมื่อ ~20 แบบ; หรือใช้ deflated Sharpe ratio)
3. **ห้ามเลือกวันเริ่มเอง:** `liveSince` = รอบตัดสินใจแรกของยุคข้อมูล (ระบบกำหนด ไม่ใช่ผู้ใช้) · ห้าม reset ยุคข้อมูล (`--replace-demo`/seed) ระหว่างนับ — ถ้าจำเป็นต้องเผยแพร่เหตุผลและผลของยุคก่อนด้วย
4. **ห้ามจูนหลังเห็นผล live:** config_th / signals_policy / stops_policy ต้องเท่ากับที่ล็อกไว้ตลอดช่วง (เทียบ hash ที่บันทึกในขั้น 3)
5. **ห้ามทิ้งผลที่แพ้:** รายงาน evidence และ track record ของ trial ที่แพ้เผยแพร่คู่กันเสมอ
6. **แยก in-sample ออกจาก out-of-sample:** ผลขั้น 2 (ข้อมูลที่เห็นแล้ว + survivorship) ใช้ตัดทางที่แย่ทิ้งเท่านั้น — หลักฐานจริงคือผลขั้น 4 ที่เกิด "หลัง" วันล็อกกติกา
7. **ต้นทุนจริง:** ใช้ต้นทุน 0.7%/ขา (commission + slippage) เป็นอย่างต่ำ — หุ้นนอก SET100 slippage สูงกว่านี้ · ผลที่หายไปเมื่อเพิ่มต้นทุนเล็กน้อย = ไม่มี edge ที่ใช้ได้จริง

## แผนที่คะแนนหลักฐาน (ตีความแบบซื่อตรง)

| สถานะ | สิ่งที่ต้องมีจริง | คะแนนหลักฐานที่สมเหตุสมผล |
|---|---|---|
| ปัจจุบัน | เครื่องมือครบ แต่ข้อมูลจำลอง/fixture · ไม่มี live record | 3/10 (เครื่องมือดี ≠ หลักฐาน) |
| ข้อมูลจริง 5 ปี + evidence-real ป้าย REAL + prereg ล็อก | in-sample ผ่าน/ไม่ผ่านตามตาราง · ยังไม่มี live | 4–5/10 (ขึ้นกับผล — "ไม่มี edge" ก็เป็นผลที่ซื่อตรง) |
| live ≥ 60 วัน + ≥ 30 เทรด บนกติกาที่ล็อก | track record REAL · LIVE · audit ผ่าน | 5–6/10 ถ้ายังไม่มีนัยสำคัญ · สูงกว่านี้ต้องมีนัยสำคัญ |
| live 6–12 เดือน · PROMISING ต่อเนื่อง · hash เผยแพร่สม่ำเสมอ · ผ่านการปรับหลาย trial | หลักฐานนอกตัวอย่างที่ตรวจย้อนได้ | 7–8/10 |
