**เน้นการนำระบบไปใช้ลงทุนหุ้นไทยจริง**

ระบบที่เราสร้างมาเหมาะกับตลาดไทยค่อนข้างดี เพราะตลาด SET มีลักษณะ **momentum + liquidity-driven** ชัดเจน แต่ก็มีจุดที่ต้องปรับให้เข้ากับสภาพจริงของไทย

---

### 1. จุดแข็งของระบบนี้กับตลาดไทย

| ลักษณะตลาดไทย | ระบบเรารองรับอย่างไร |
|--------------|---------------------|
| หุ้นขนาดกลาง-เล็กมี momentum แรง | Multi-timeframe ranking + liquidity filter |
| เงินหมุนเร็ว เปลี่ยนตัวบ่อย | Overlap Ratio / Regime detection |
| Slippage สูงนอก SET100 | Dynamic slippage ตาม ADV + participation cap |
| Retail เยอะ → overreact | Meta-labeling ช่วยกรองสัญญาณคุณภาพต่ำ |
| ข้อมูลย้อนหลังหาได้จาก Amibroker | Backfill + snapshot pipeline พร้อมใช้ |

### 2. การตั้งค่าที่แนะนำสำหรับหุ้นไทย (ปรับจากของเดิม)

```python
# config.py — ค่าที่เหมาะกับ SET มากกว่า

MIN_PRICE = 1.5                    # เลี่ยงหุ้นราคาต่ำมาก
MIN_VALUE_5D = 3_000_000           # อย่างน้อย 3 ล้านบาท/วัน ติดกัน 5 วัน (เดิม 1 ล้าน)
# หรือใช้ 5 ล้าน ถ้าเน้น SET100 เป็นหลัก

TIMEFRAMES = [5, 10, 20, 40, 60, 120]   # ตัด 160/300 ออก หรือเก็บไว้เป็น long-only view
TOP_N = 25

STRATEGY = {
    "k": 3,                        # ติดอย่างน้อย 3 โผ (สมดุลดีในไทย)
    "hold": 8,                     # 8–12 วัน เหมาะกับ momentum ไทย
    "stop": 0.09,                  # 9% (ตลาดไทยแกว่งแรง)
    "max_pos": 7,                  # อย่าเกิน 7–8 ตัว (correlation สูง)
    "cost_bps": 30,                # commission ประมาณนี้
    "slip_bps_base": 40,           # ฐาน slippage สูงกว่าตลาดใหญ่
}

RISK = {
    "max_weekly_dd": -0.05,        # เข้มงวดขึ้น
    "vol_target": 0.13,
    "trade_baht": 40_000,          # ต่อไม้ (ปรับตามเงินทุน)
    "max_participation": 0.04,     # ไม่เกิน 4% ของ ADV
}
```

**คำแนะนำเพิ่ม:**
- เน้นหุ้นใน **SET100 + บางตัวใน mai ที่ volume สูงจริง**
- ตัดหุ้นที่ถูกขึ้นเครื่องหมาย (C, SP, H) หรือมี corporate action ใกล้ ๆ
- หลีกเลี่ยงช่วงก่อน/หลังประกาศงบถ้ายังไม่มี filter พิเศษ

### 3. ขั้นตอนนำไปใช้จริงกับพอร์ตหุ้นไทย

#### เฟส 1: วิจัยและพิสูจน์ (2–4 สัปดาห์)
1. Backfill ข้อมูลจาก Amibroker ย้อนหลังอย่างน้อย 3 ปี
2. รัน  
   ```bash
   python run_profit_engine.py
   python run_advanced_research.py
   ```
3. ดูผลโดยเฉพาะ:
   - Long-Short gap จาก CPCV
   - CAGR / MaxDD / Sharpe หลังต้นทุน 100bps
   - ความเสถียรข้ามครึ่งเวลา

#### เฟส 2: Paper Trading (อย่างน้อย 8–12 สัปดาห์)
- ตั้ง `JEV_PAPER=1`
- รัน daily chain ทุกวันหลังตลาดปิด
- บันทึกทั้งสัญญาณที่ระบบเลือก + สิ่งที่คุณจะทำจริง
- เปรียบเทียบ performance กับ SET Index และ SET100

#### เฟส 3: เงินจริงขนาดเล็ก
- เริ่มด้วยเงินไม่เกิน 10–15% ของพอร์ตรวม
- ใช้ max_pos = 5–6 ตัวก่อน
- บังคับใช้ stop และ kill-switch รายสัปดาห์

### 4. ความเสี่ยงเฉพาะตลาดไทยที่ต้องระวัง

| ความเสี่ยง | วิธีรับมือในระบบ |
|-----------|------------------|
| Slippage และ spread กว้าง | ใช้ `MIN_VALUE_5D` สูง + participation cap |
| หุ้นกระจุกตัวภาค (ธนาคาร, พลังงาน, อสังหา) | Cluster Risk Parity ใน `portfolio_adv.py` |
| Gap ลงจากข่าวร้ายข้ามคืน | Stop แบบเปอร์เซ็นต์ + ไม่ถือเยอะก่อนวันหยุดยาว |
| Window dressing / ปลายไตรมาส | ลดขนาดช่วงปลายเดือน/ปลายไตรมาส |
| หุ้นถูกควบคุมหรือมีข่าวภายใน | Human gate สำหรับไม้ขนาดใหญ่หรือกำไรเกิน 25% |
| ข้อมูล delisted / adjusted ไม่ครบ | ตรวจ DQ ทุกวัน + ใช้ adjusted price จาก Amibroker |

### 5. สไตล์การใช้ที่เหมาะกับคนไทยทั่วไป

**แบบที่แนะนำที่สุดสำหรับผู้ใช้คนเดียว:**

- ใช้ระบบเป็น **ตัวกรอง + จัดอันดับ** ไม่ใช่ระบบอัตโนมัติ 100%
- ทุกวันหลังปิดตลาด ดูสรุปจาก Jev
- เลือกเข้าเฉพาะตัวที่:
  - ติด ≥ 3 timeframe
  - ผ่าน liquidity
  - Meta-model ให้คะแนนปานกลางขึ้นไป (ถ้าเปิดใช้)
  - ไม่ขัดกับมุมมองภาพรวมตลาดของคุณ
- ถือตาม hold period ที่กำหนด + ตัดขาดทุนตามระบบ
- ทบทวนรายสัปดาห์ (review ritual) ว่า human decision ดีกว่า auto หรือไม่

### 6. จุดที่ควรพัฒนาต่อเฉพาะตลาดไทย

1. **Sector / Industry neutralization** — ไม่ให้พอร์ตกระจุกแค่ 1–2 กลุ่มอุตสาหกรรม
2. **Earnings calendar filter** — หลีกเลี่ยงช่วงก่อนงบถ้ายังไม่มี edge ชัด
3. **SET Index regime** — ใช้สถานะตลาดกว้าง (Bull/Bear/Sideways) มาปรับ gross exposure
4. **Calibrate slippage จริง** — เก็บข้อมูล order ที่ส่งจริง แล้วปรับโมเดล slip_bps
5. **Watchlist เฉพาะทาง** — เช่น เฉพาะหุ้นที่อยู่ในกองทุนรวมหรือมี foreign room

### 1. ทำไมการกระจายความเสี่ยงถึงสำคัญมากในตลาดไทย

ตลาดหุ้นไทยมีลักษณะเด่นที่ทำให้ “ถือหลายตัว” ไม่ได้แปลว่ากระจายความเสี่ยงจริง:

- หุ้นมักวิ่งเป็น**กลุ่มอุตสาหกรรม**ชัดเจน (Banking, Energy, Property)
- Correlation ระหว่างหุ้นสูงขึ้นมากในภาวะตลาดตก
- หุ้นขนาดกลาง-เล็กมี liquidity risk และ gap risk สูง
- Retail มีอิทธิพลสูง → sentiment เปลี่ยนพร้อมกันทั้งกระดาน

ดังนั้นการกระจายความเสี่ยงที่ดีต้องทำมากกว่าการถือคนละตัว

### 2. ระดับของการกระจายความเสี่ยง (จากพื้นฐาน → ขั้นสูง)

| ระดับ | เทคนิค | สิ่งที่กระจาย | ข้อจำกัดในไทย |
|------|--------|-------------|----------------|
| 1 | จำนวนหุ้น | ชื่อหุ้น | Correlation สูง → ได้ผลน้อย |
| 2 | อุตสาหกรรม (Sector) | กลุ่มธุรกิจ | ที่เราทำไปแล้ว (≤30% ต่อ sector) |
| 3 | กลุ่มอุตสาหกรรมสัมพันธ์ (Sector Group) | กลุ่มที่มักวิ่งด้วยกัน | ที่เพิ่งเพิ่ม (Financials, EnergyComplex ฯลฯ) |
| 4 | ปัจจัยความเสี่ยง (Factor) | Momentum, Value, Size, Volatility | ต้องมีโมเดล factor |
| 5 | ความผันผวน (Volatility Targeting) | ขนาดความเสี่ยงต่อตัว/พอร์ต | มีในระบบแล้ว |
| 6 | Hierarchical Risk Parity / Clustering | กลุ่มที่เคลื่อนไหวคล้ายกันจากข้อมูล | มีโครงใน `portfolio_adv.py` |
| 7 | Effective Number of Bets (Eff-N) | จำนวนการเดิมพันที่ “อิสระ” จริง | มีใน `risk.py` |
| 8 | Time diversification | เวลาเข้า-ออก, rebalance | ผ่าน hold period + regime |

### 3. เทคนิคสำคัญเรียงตามประสิทธิภาพจริง

### 3.1 Sector & Sector-Group Limits (ที่ระบบมีแล้ว)
- จำกัดน้ำหนักต่อ industry
- จำกัดน้ำหนักรวมของกลุ่มที่ correl สูง (Banking+Finance, Energy+Material ฯลฯ)
- **ข้อดี**: เข้าใจง่าย บังคับใช้ได้ทันที ป้องกันความเสี่ยงกระจุกตัวแบบคลาสสิก

### 3.2 Volatility Targeting / Risk Budgeting
แต่ละตัวไม่ได้ใส่เงินเท่ากัน แต่ใส่ตามความผันผวน

\[
w_i \propto \frac{1}{\sigma_i}
\]

หรือแบบ risk parity ทั้งพอร์ต:

\[
w_i \cdot \sigma_i = \text{constant}
\]

**ข้อดีในไทย**: หุ้นเล็กมักผันผวนสูง → ระบบจะลดน้ำหนักให้อัตโนมัติ ลดโอกาสถูกกระทบหนักจากตัวเดียว

### 3.3 Correlation Clustering / Hierarchical Risk Parity (HRP)
แทนการสมมติว่าหุ้นอิสระจากกัน ระบบจัดกลุ่มหุ้นที่เคลื่อนไหวคล้ายกันจาก correlation matrix แล้วแบ่งงบประมาณความเสี่ยงเท่า ๆ กันต่อคลัสเตอร์

**ข้อดี**: จับความสัมพันธ์ที่เปลี่ยนตามเวลาได้ดีกว่า sector แบบคงที่  
**ข้อจำกัด**: ต้องการข้อมูลย้อนหลังเพียงพอและต้องอัปเดตเป็นระยะ

### 3.4 Effective Number of Bets (Eff-N)
สูตรโดยประมาณ:

\[
N_{\text{eff}} = \frac{1}{\mathbf{w}^T \Sigma \mathbf{w} / \bar{\sigma}^2} \quad \text{หรือจาก correlation matrix}
\]

ถ้าถือ 10 ตัว แต่ Eff-N = 3.2 แปลว่าจริง ๆ แล้วคุณเดิมพันแค่ประมาณ 3 กลุ่มความเสี่ยง

ระบบเรามีฟังก์ชันนี้ใน `decision/risk.py` แล้ว

### 3.5 Regime-based Gross Exposure
ในภาวะที่ Overlap Ratio สูง (ตลาดมี trend ชัด) → เพิ่มขนาดพอร์ต  
ในภาวะที่เงินหมุนรายตัวหรือ correlation พุ่ง → ลดขนาดพอร์ตรวม

นี่คือการกระจายความเสี่ยงในมิติ “เวลา”

### 3.6 Factor Diversification (ขั้นสูง)
กระจายไปยังปัจจัยที่ต่างกัน เช่น
- Momentum (ระบบหลักของเรา)
- Low Volatility
- Quality / Profitability
- Value (ถ้ามีข้อมูล)

การถือแต่ momentum อย่างเดียวจะเสี่ยงตอน momentum crash

### 7. สรุปหลักการที่ควรยึด

> การกระจายความเสี่ยงที่ดีไม่ใช่การถือเยอะที่สุด  
> แต่คือการทำให้ **ความเสียหายจากเหตุการณ์เดียวกระทบพอร์ตได้น้อยที่สุด**  
> ในขณะที่ยังรักษา edge ของกลยุทธ์หลักไว้

ในระบบของเราตอนนี้มีการกระจาย 3 ชั้นหลักแล้ว:
1. ระดับตัวหุ้น (liquidity + vol sizing)
2. ระดับอุตสาหกรรมและกลุ่มอุตสาหกรรม
3. ระดับพอร์ต (kill-switch + regime)

ต้องการให้ผมเจาะลึกส่วนไหนต่อเป็นพิเศษไหมครับ?

- Hierarchical Risk Parity แบบละเอียด + วิธีคำนวณ  
- การวัด Effective-N และการตั้งเป้า  
- การเพิ่ม Factor อื่นเข้ามาคู่กับ Momentum  
- หรือออกแบบกฎกระจายความเสี่ยงแบบเฉพาะสำหรับพอร์ตขนาดของคุณ**Hierarchical Risk Parity (HRP)**  
เทคนิคการจัดน้ำหนักพอร์ตที่พัฒนาโดย **Marcos López de Prado** (2016) เพื่อแก้จุดอ่อนสำคัญของ Mean-Variance Optimization และ Risk Parity แบบดั้งเดิม

---

### 1. ทำไมต้องมี HRP

| ปัญหาของวิธีเดิม | ผลกระทบ |
|------------------|---------|
| **Mean-Variance (Markowitz)** | อ่อนไหวมากต่อค่าประมาณ correlation และ expected return → น้ำหนักกระโดดแรง |
| **Inverse Volatility** | มองข้าม correlation ระหว่างสินทรัพย์ |
| **Classical Risk Parity** | ต้องกลับ matrix (inversion) → ไม่เสถียรเมื่อหุ้น correl สูงหรือจำนวนมาก |
| **Equal Weight** | ไม่สนใจทั้งความผันผวนและ correlation |

HRP ถูกออกแบบมาเพื่อ:
- **ไม่ต้อง invert matrix**
- ใช้โครงสร้าง hierarchical ของ correlation
- เสถียรกว่าเมื่อจำนวนหุ้นมากและ correl เปลี่ยนบ่อย (เหมาะกับตลาดไทย)

---

### 2. แนวคิดหลักของ HRP

แทนที่จะมองหุ้นทุกตัวเป็นอิสระจากกัน HRP มองว่าหุ้นสร้าง**ต้นไม้ลำดับชั้น (hierarchy)** ตามความคล้ายคลึงของการเคลื่อนไหว

ขั้นตอนหลักมี 3 ขั้น:

1. **Tree Clustering** — สร้างต้นไม้จาก distance matrix  
2. **Quasi-Diagonalization** — จัดเรียง correlation matrix ใหม่ให้คล้าย ๆ กันอยู่ใกล้กัน  
3. **Recursive Bisection** — แบ่งงบประมาณความเสี่ยงลงไปตามกิ่งของต้นไม้

---

### 3. ขั้นตอนละเอียด

### ขั้นที่ 1: สร้าง Distance Matrix จาก Correlation

จาก correlation matrix \(\rho\) เราแปลงเป็นระยะทาง:

\[
d_{ij} = \sqrt{\frac{1}{2}(1 - \rho_{ij})}
\]

- \(\rho = 1\) → \(d = 0\) (เหมือนกันทุกอย่าง)  
- \(\rho = -1\) → \(d = 1\) (ตรงข้ามสุด)

จากนั้นใช้ **Hierarchical Clustering** (มักใช้ Single, Complete หรือ Ward linkage) สร้าง dendrogram

### ขั้นที่ 2: Quasi-Diagonalization

จัดเรียงลำดับของสินทรัพย์ใหม่ตามใบของต้นไม้ (seriation)  
ทำให้ correlation matrix หลังจัดเรียงมีค่าสูงอยู่ใกล้เส้นทแยงมุม → เห็นโครงสร้างกลุ่มชัดขึ้น

### ขั้นที่ 3: Recursive Bisection (หัวใจของ HRP)

เริ่มจากทั้งพอร์ต แล้วแบ่งเป็น 2 กลุ่มตามต้นไม้ซ้ำ ๆ

ที่แต่ละจุดแบ่ง:

- คำนวณ cluster variance ของแต่ละฝั่ง  
- จัดสรรงบประมาณความเสี่ยงแบบ inverse-variance ระหว่างสองฝั่ง

สูตรที่ใช้บ่อย:

\[
\alpha_1 = \frac{1 / \tilde{V}_1}{1/\tilde{V}_1 + 1/\tilde{V}_2}, \quad \alpha_2 = 1 - \alpha_1
\]

โดย \(\tilde{V}_i\) คือ variance ของ cluster \(i\) (คำนวณจากน้ำหนักภายใน cluster นั้น)

ทำแบบนี้ลงไปจนถึงระดับใบ (หุ้นแต่ละตัว) จะได้น้ำหนักสุดท้าย

---

### 4. ภาพรวมอัลกอริทึมแบบย่อ

```
1. คำนวณ correlation matrix จาก returns
2. แปลงเป็น distance matrix
3. Hierarchical clustering → ได้ linkage matrix (ต้นไม้)
4. เรียงลำดับหุ้นตามใบของต้นไม้ (quasi-diagonalize)
5. Recursive bisection:
   - แบ่งกลุ่มตามต้นไม้
   - ปันส่วน risk budget แบบ inverse-variance ระหว่างกลุ่ม
   - ทำซ้ำจนถึงหุ้นรายตัว
6. ได้น้ำหนัก w ที่รวมกัน = 1
```

---

### 5. จุดเด่นของ HRP

| ข้อดี | คำอธิบาย |
|------|---------|
| ไม่ต้อง invert matrix | เสถียรเมื่อหุ้นเยอะหรือ correl สูง |
| ใช้ข้อมูล correlation จริง | จับกลุ่มที่ตลาดมองว่าคล้ายกัน ไม่ใช่แค่ sector ทางการ |
| Out-of-sample ดีกว่า Markowitz ในหลายการศึกษา | โดยเฉพาะเมื่อ expected return ประมาณยาก |
| ตีความได้ | เห็นโครงสร้างกลุ่มจาก dendrogram |
| เหมาะกับตลาดเกิดใหม่ | รวมถึงไทยที่ sector correlation เปลี่ยนตามวัฏจักร |

### 6. ข้อจำกัดที่ต้องรู้

1. **ยังพึ่งพา correlation ในอดีต** — ถ้าโครงสร้างตลาดเปลี่ยนฉับพลัน (regime shift) อาจช้า
2. **ไม่มี view เรื่อง expected return** — เป็นการกระจายความเสี่ยงล้วน ๆ ไม่ได้ maximize return
3. **การเลือก linkage และ lookback window มีผล** — ต้องทดสอบความเสถียร
4. **ไม่ได้แก้ปัญหา liquidity และ transaction cost โดยตรง** — ต้องซ้อนชั้น participation cap เพิ่ม
5. **Interpretation ยากกว่า equal-weight หรือ sector limit** สำหรับผู้ไม่คุ้นเคย

- ยังไม่ได้ทำ full recursive bisection แบบต้นฉบับ

ความแตกต่างหลัก:

| จุด | ของเราตอนนี้ | Full HRP |
|----|-------------|----------|

### 8. สูตรสำคัญที่เกี่ยวข้อง

**Cluster variance** (แบบง่าย):

\[
\tilde{V}_i = w_i^\top V_i w_i
\]

โดย \(w_i\) คือน้ำหนักภายใน cluster (มักเริ่มจาก inverse-volatility)

**ระยะทาง correlation**:

\[
d_{ij} = \sqrt{\frac{1}{2}(1-\rho_{ij})}
\]

**Effective Number of Bets** (ใช้คู่กับ HRP เพื่อตรวจสอบ):

\[
N_{\text{eff}} = \left( \sum_{i=1}^n w_i^2 \right)^{-1}
\]

หรือแบบใช้ correlation matrix ก็ได้

### 1. นิยามสั้น ๆ

| แนวทาง | คำนิยามหลัก |
|--------|------------|
| **Risk Parity (RP)** | ทำให้**แต่ละสินทรัพย์** (หรือแต่ละกลุ่มที่กำหนดไว้ล่วงหน้า) ส่งผลต่อความเสี่ยงของพอร์ตเท่า ๆ กัน |
| **Hierarchical Risk Parity (HRP)** | ทำให้**แต่ละกลุ่มในโครงสร้างลำดับชั้น** (ที่สร้างจาก correlation) ส่งผลต่อความเสี่ยงเท่า ๆ กัน โดยไม่ต้อง invert matrix |

### 2. เป้าหมายทางคณิตศาสตร์

### Risk Parityคลาสสิก
ต้องการให้ Risk Contribution เท่ากัน:

\[
w_i \cdot \frac{\partial \sigma_p}{\partial w_i} = \frac{\sigma_p}{n} \quad \forall i
\]

หรือในรูปแบบง่าย (เมื่อสมมติ correlation คงที่) จะกลายเป็น **Inverse Volatility**:

\[
w_i \propto \frac{1}{\sigma_i}
\]

ถ้าเป็น Full Risk Parity จริง จะต้องแก้ระบบสมการที่ใช้ covariance matrix (มักมี matrix inversion หรือ optimization)

### Hierarchical Risk Parity
ไม่พยายามทำให้ risk contribution ของทุกตัวเท่ากันโดยตรง  
แต่ใช้ขั้นตอน:

1. สร้างต้นไม้จาก correlation  
2. จัดเรียงใหม่ (quasi-diagonalization)  
3. แบ่งงบประมาณความเสี่ยงแบบ recursive inverse-variance ตามกิ่งของต้นไม้

ผลลัพธ์คือน้ำหนักที่สะท้อนโครงสร้างกลุ่มมากกว่าการบังคับให้ทุกตัวเท่ากัน

---

### 3. ตารางเปรียบเทียบโดยตรง

| มิติ | Risk Parity (RP) | Hierarchical Risk Parity (HRP) |
|------|------------------|--------------------------------|
| **หน่วยที่กระจายความเสี่ยง** | รายสินทรัพย์ (หรือกลุ่มที่กำหนดเอง) | กลุ่มตาม hierarchy ของ correlation |
| **ใช้ correlation** | ใช้เต็มรูปแบบ (Full RP) หรือแทบไม่ใช้ (Inverse Vol) | ใช้ผ่านโครงสร้างต้นไม้ |
| **Matrix inversion** | ต้องการ (Full RP) | **ไม่ต้องการ** |
| **ความเสถียรของน้ำหนัก** | ต่ำถึงปานกลาง (โดยเฉพาะ Full RP) | สูงกว่า โดยทั่วไป |
| **ความอ่อนไหวต่อ estimation error** | สูง | ต่ำกว่า |
| **การตีความ** | ค่อนข้างตรงไปตรงมา | ต้องดู dendrogram ประกอบ |
| **Expected Return** | ไม่ใช้ | ไม่ใช้ |
| **จำนวนสินทรัพย์มาก** | ยิ่งเยอะยิ่งมีปัญหา numerical | รับได้ดีกว่า |
| **การเปลี่ยนโครงสร้างตลาด** | ปรับช้า / น้ำหนักกระโดด | ปรับผ่านการ re-cluster |

### Risk Parity
**จุดแข็ง**
- แนวคิดเรียบง่าย เข้าใจง่าย
- Inverse Volatility ใช้ได้ทันที ไม่ซับซ้อน
- ทำงานดีเมื่อสินทรัพย์มี correlation ต่ำถึงปานกลางและเสถียร

**จุดอ่อน**
- Full RP อ่อนไหวต่อ estimation error ของ covariance
- มองข้ามโครงสร้างกลุ่ม (หุ้นใน sector เดียวกันยังได้น้ำหนักสูงรวมกันได้)
- ในตลาดที่ correlation พุ่งพร้อมกัน (เช่น ตลาดไทยตอนวิกฤต) การกระจายความเสี่ยงเสื่อมลงเร็ว

### Hierarchical Risk Parity
**จุดแข็ง**
- ไม่ต้อง invert matrix → เสถียรกว่าเมื่อหุ้นเยอะ
- จับกลุ่มหุ้นที่เคลื่อนไหวด้วยกันจากข้อมูลจริง
- ลดปัญหา “ดูเหมือนกระจาย แต่จริง ๆ กระจุกในปัจจัยเดียว”
- มีงานวิจัยรองรับว่า out-of-sample ดีกว่า Markowitz ในหลายกรณี

**จุดอ่อน**
- ซับซ้อนกว่าในการอธิบายและ implement
- ผลลัพธ์ขึ้นกับ lookback period และวิธี linkage
- ไม่มีมุมมองเรื่องผลตอบแทนที่คาดหวัง (เหมือน RP)
- ยังพึ่งพา correlation ในอดีต

### 5. ตัวอย่างแนวคิดด้วยตัวเลขง่าย ๆ

สมมติมีหุ้น 4 ตัว:

- A, B อยู่ในกลุ่มธนาคาร (correl สูงมาก)
- C, D อยู่ในกลุ่มอื่น (correl ต่ำ)

**Inverse Volatility / RP ง่าย ๆ**  
อาจให้น้ำหนัก A+B รวมกันสูงถึง 45–50% เพราะแต่ละตัวผันผวนไม่สูง

**HRP**  
จะมอง A กับ B เป็นกิ่งเดียวกันในต้นไม้ แล้วจำกัดงบประมาณความเสี่ยงของทั้งกิ่ง → น้ำหนักรวมของกลุ่มธนาคารถูกกดลงโดยอัตโนมัติ แม้แต่ละตัวจะดูไม่ผันผวนมาก

นี่คือข้อแตกต่างสำคัญในทางปฏิบัติ

**เปรียบเทียบ Hierarchical Risk Parity (HRP) กับ Black-Litterman (BL)**

ทั้งสองเป็นเทคนิคจัดน้ำหนักพอร์ตที่สำคัญ แต่เกิดจากปัญหาคนละแบบและแก้คนละจุด

### 1. ภาพรวมสั้น ๆ

| มิติ | Hierarchical Risk Parity (HRP) | Black-Litterman (BL) |
|------|--------------------------------|----------------------|
| **ผู้พัฒนา** | Marcos López de Prado (2016) | Fischer Black & Robert Litterman (1990–1992) |
| **ปัญหาหลักที่แก้** | ความไม่เสถียรของ Mean-Variance และการ invert covariance | Expected return ประมาณยาก และน้ำหนักกระจุกผิดปกติ |
| **จุดเน้น** | การกระจาย**ความเสี่ยง**ตามโครงสร้าง correlation | การรวม**มุมมอง** (views) เข้ากับตลาดอย่างมีหลักการ |
| **ใช้ Expected Return** | ไม่ใช้ | ใช้ (ทั้งจากตลาดและจากผู้ลงทุน) |
| **ใช้ Covariance** | ใช้ผ่าน hierarchy (ไม่ invert โดยตรง) | ใช้เต็มรูปแบบ |

### 2. ปรัชญาและเป้าหมาย

**HRP**  
> “ไม่พยายามทายผลตอบแทน แค่กระจายความเสี่ยงให้สอดคล้องกับโครงสร้างธรรมชาติของตลาด”

**Black-Litterman**  
> “เริ่มจากตลาดที่เป็น equilibrium แล้วปรับด้วยมุมมองของเราอย่างมีน้ำหนักตามความมั่นใจ”

BL จึงเป็น Bayesian framework สำหรับ expected return  
HRP เป็น risk-based allocation ที่เลี่ยงการพึ่ง expected return

| ข้อมูล | HRP | Black-Litterman |

### HRP
1. คำนวณ correlation → แปลงเป็น distance

ผลลัพธ์: น้ำหนักที่เบี่ยงจากตลาดตาม views และระดับความมั่นใจ

### 6. จุดแข็ง–จุดอ่อน

### Hierarchical Risk Parity
**จุดแข็ง**
- ไม่ต้องทาย return → ลดแหล่ง error ใหญ่ที่สุด
- ไม่ต้อง invert matrix โดยตรง → เสถียรเมื่อหุ้นเยอะ
- จับโครงสร้างกลุ่มจากข้อมูลจริง
- เหมาะเป็นชั้น “กระจายความเสี่ยง” หลังคัดหุ้นแล้ว

**จุดอ่อน**
- ไม่มีกลไกใส่ alpha/views โดยตรง
- ยังพึ่ง correlation ในอดีต
- ไม่ได้ optimize ผลตอบแทนที่คาดหวัง

### Black-Litterman
**จุดแข็ง**
- มีทฤษฎีรองรับชัด (Bayesian + equilibrium)
- ใส่ views ได้ทั้งแบบ absolute และ relative
- ควบคุมผลกระทบของ view ด้วยระดับความมั่นใจ
- น้ำหนักไม่ออกแนวสุดโต่งง่ายเหมือน Markowitz ตรง ๆ

**จุดอ่อน**
- ต้องกำหนด views และความมั่นใจ → อคติมนุษย์เข้ามาได้
- พารามิเตอร์ τ และ uncertainty matrix มีผลมาก
- ยังต้องพึ่ง covariance ที่ประมาณจากอดีต
- implement และ calibrate ยากกว่า HRP

ต้องการให้เจาะต่อในมุมไหนเพิ่มเติมไหมครับ?  
เช่น สูตรหลักของ Black-Litterman, วิธีแปลงสัญญาณ momentum เป็น BL views, หรือการออกแบบ hybrid HRP + BL สำหรับพอร์ตไทย**Black-Litterman Formulas Explained**

The Black-Litterman (BL) model combines two sources of information about expected returns:

1. **Market equilibrium** (implied by current market-cap weights)
2. **Investor views** (your subjective forecasts)

It does this in a Bayesian way, so the final expected returns are a confidence-weighted blend of the two.

---

### 1. Core Idea in One Sentence

> Start from the returns that would make the market portfolio optimal, then tilt those returns according to your views, where the size of the tilt depends on how confident you are.

---

### 2. Step-by-Step Formulas

### Step 1: Reverse Optimization → Equilibrium Returns

From mean-variance optimization, the optimal weights satisfy:

\[
w = \frac{1}{\lambda} \Sigma^{-1} \mu
\]

Solving for \(\mu\) (reverse optimization):

\[
\Pi = \lambda \Sigma w_{\text{mkt}}
\]

Where:
- \(\Pi\) = equilibrium expected excess returns (vector)
- \(\lambda\) = risk aversion coefficient
- \(\Sigma\) = covariance matrix of excess returns
- \(w_{\text{mkt}}\) = market-cap weights (sum to 1)

**How to get \(\lambda\)** (common practical choice):

\[
\lambda = \frac{E[r_m] - r_f}{\sigma_m^2}
\]

Or simply set a reasonable value (e.g. 2.5–3.5 for equities).

---

### Step 2: Express Your Views

Views are written in matrix form:

\[
P \mu = Q + \varepsilon, \quad \varepsilon \sim N(0, \Omega)
\]

- \(P\) = pick matrix (\(k \times n\)), selects which assets the views refer to  
- \(Q\) = view returns (\(k \times 1\))  
- \(\Omega\) = uncertainty (confidence) matrix of the views (\(k \times k\))

**Examples**

Absolute view: “Asset 3 will return 5%”  
\[
P = [0,\ 0,\ 1,\ 0], \quad Q = [0.05]
\]

Relative view: “Asset 1 will outperform Asset 2 by 2%”  
\[
P = [1,\ -1,\ 0,\ 0], \quad Q = [0.02]
\]

---

### Step 3: The Black-Litterman Master Formula

The posterior expected returns \(\mu_{\text{BL}}\) are:

\[
\mu_{\text{BL}} = \Pi + \tau \Sigma P^\top \left( P \tau \Sigma P^\top + \Omega \right)^{-1} (Q - P \Pi)
\]

Or in the more compact “precision-weighted” form:

\[
\mu_{\text{BL}} = \left( (\tau \Sigma)^{-1} + P^\top \Omega^{-1} P \right)^{-1} \left( (\tau \Sigma)^{-1} \Pi + P^\top \Omega^{-1} Q \right)
\]

Both formulas are mathematically equivalent.

**Interpretation of the terms**
- \(\tau \Sigma\) = uncertainty of the equilibrium returns (prior variance)
- \(\Omega\) = uncertainty of your views
- The formula pulls \(\Pi\) toward your views \(Q\), with the strength of the pull controlled by the relative confidences.

---

### Step 4: Key Parameters

| Parameter | Meaning | Typical choices |
|-----------|---------|-----------------|
| \(\tau\) | Scales the uncertainty of the prior | 0.01 – 0.05 (most common), or \(1/T\) |
| \(\Omega\) | Uncertainty of views | Diagonal matrix; higher value = less confidence |
| \(\lambda\) | Risk aversion | 2.0 – 4.0 for equity portfolios |

**Common simple rule for \(\Omega\)** (Idzorek style):

\[
\Omega_{ii} = \tau \cdot P_i \Sigma P_i^\top \cdot \left(\frac{1}{c_i} - 1\right)
\]

or even simpler:

\[
\Omega = \text{diag}(P \tau \Sigma P^\top)
\]

(this assumes view uncertainty is proportional to the variance of the view portfolio).

---

### Step 5: Posterior Covariance (Optional but Recommended)

The uncertainty of the posterior mean is:

\[
\Sigma_{\text{BL}} = \left( (\tau \Sigma)^{-1} + P^\top \Omega^{-1} P \right)^{-1}
\]

Some practitioners then use the updated covariance for optimization:

\[
\Sigma_{\text{posterior}} = \Sigma + \Sigma_{\text{BL}}
\]

---

### Step 6: Final Portfolio Optimization

Once you have \(\mu_{\text{BL}}\), you run a normal mean-variance optimization:

\[
w^* = \arg\max_w \; w^\top \mu_{\text{BL}} - \frac{\lambda}{2} w^\top \Sigma w
\]

subject to whatever constraints you want (long-only, sector limits, etc.).

Closed-form unconstrained solution:

\[
w^* = \frac{1}{\lambda} \Sigma^{-1} \mu_{\text{BL}}
\]

---

### 3. Intuitive Flow

```
Market-cap weights
       ↓
Reverse optimization → Equilibrium returns Π
       ↓
Your views (P, Q) + confidence (Ω)
       ↓
Bayesian update → μ_BL
       ↓
Mean-variance optimization → Final weights
```

---

### 4. Practical Tips

1. **τ is the most sensitive parameter** — keep it small (0.01–0.05). Large τ makes the prior very uncertain and lets views dominate.
2. Start with only a few high-conviction views. Too many views re-introduces estimation error.
3. Relative views are usually more reliable than absolute views.
4. Always check that the resulting weights do not become extreme; add constraints if needed.
5. In a momentum system, a natural way to create views is:
   - Let the magnitude of the momentum signal (or meta-model probability) determine \(Q\)
   - Let the confidence of the signal determine the diagonal entries of \(\Omega\)

| Unconstrained weights | \(w = \frac{1}{\lambda} \Sigma^{-1} \mu_{\text{BL}}\) |

**Idzorek’s Method for Specifying View Confidence in Black-Litterman**

Thomas Idzorek (2002, 2005) proposed a practical and intuitive way to set the **view uncertainty matrix \(\Omega\)** in the Black-Litterman model.  

The original Black-Litterman framework leaves \(\Omega\) largely to the user’s judgment, which is hard to calibrate. Idzorek’s method replaces that judgment with a more natural concept: **percentage confidence** in each view.

---

### 1. The Problem It Solves

In the classic BL formula we need:

\[
\Omega = \text{uncertainty (variance) of the views}
\]

Most people do not think in terms of variance of a view. They think:

> “I am 70% confident in this view.”

Idzorek’s method translates that percentage confidence into the correct diagonal entry of \(\Omega\).

---

### 2. Core Idea

For each view \(i\):

1. Compute the portfolio weights that would result if we treated the view as **100% certain**.
2. Compute the portfolio weights that result from the **equilibrium only** (no views).
3. The final weights should lie somewhere between these two extremes, according to the user’s confidence \(c_i\) (where \(0 < c_i \leq 1\)).
4. Back out the value of \(\omega_i\) (the diagonal element of \(\Omega\)) that produces exactly that blend.

---

### 3. Step-by-Step Procedure

#### Step 1: Compute Equilibrium Weights
Using only the equilibrium returns \(\Pi\):

\[
w_{\text{eq}} = \frac{1}{\lambda} \Sigma^{-1} \Pi
\]

(or the constrained version you actually use).

#### Step 2: Compute “100% Confident” Weights for View \(i\)
Temporarily set the uncertainty of view \(i\) to (almost) zero and solve the BL model. This gives weights \(w_{100,i}\).

#### Step 3: Target Weights According to Confidence
Idzorek defines the desired weights as a linear blend:

\[
w_{\text{target},i} = w_{\text{eq}} + c_i \, (w_{100,i} - w_{\text{eq}})
\]

where \(c_i \in (0,1]\) is the confidence level in view \(i\) (e.g. 0.6 = 60% confident).

#### Step 4: Solve for the Implied \(\omega_i\)
We need to find the scalar \(\omega_i > 0\) such that when we insert

\[
\Omega = \text{diag}(\ldots, \omega_i, \ldots)
\]

into the Black-Litterman formula, the resulting weights equal \(w_{\text{target},i}\).

This is usually done by a simple one-dimensional search (or occasionally an analytic approximation).

---

### 4. Key Formulas

The Black-Litterman posterior mean (repeated for reference):

\[
\mu_{\text{BL}} = \Pi + \tau\Sigma P^\top \bigl(P\tau\Sigma P^\top + \Omega\bigr)^{-1}(Q - P\Pi)
\]

Idzorek’s contribution is the mapping:

\[
c_i \quad \longrightarrow \quad \omega_i
\]

A useful approximate closed-form relationship (often used in practice) is:

\[
\omega_i \approx \tau \cdot (P_i \Sigma P_i^\top) \cdot \frac{1 - c_i}{c_i}
\]

When \(c_i \to 1\), \(\omega_i \to 0\) (view becomes certain).  
When \(c_i \to 0\), \(\omega_i \to \infty\) (view is ignored).

---

### 5. Practical Advantages

| Advantage | Explanation |
|---------|-------------|
| Intuitive | Users specify “I am 65% confident” instead of a variance number |
| Consistent | All views are expressed on the same confidence scale |
| Easy to explain | Clients and risk committees understand percentage confidence |
| Still Bayesian | The method stays inside the original BL mathematical framework |
| Flexible | Works with both absolute and relative views |

---

### 6. Simple Numerical Illustration

Suppose we have one relative view and set confidence \(c = 0.70\).

- Equilibrium weights: \(w_{\text{eq}} = [0.40,\ 0.35,\ 0.25]\)
- Weights if the view is 100% certain: \(w_{100} = [0.55,\ 0.25,\ 0.20]\)

Target weights at 70% confidence:

\[
w_{\text{target}} = w_{\text{eq}} + 0.70 \times (w_{100} - w_{\text{eq}}) = [0.505,\ 0.280,\ 0.215]
\]

We then search for the value of \(\omega\) that makes the BL model produce weights as close as possible to \(w_{\text{target}}\). That \(\omega\) becomes the corresponding diagonal entry of \(\Omega\).

---

### 7. Comparison with Other Ways to Set \(\Omega\)

| Method | How \(\Omega\) is set | Pros | Cons |
|--------|-----------------------|------|------|
| Original BL | User picks variances directly | Theoretically pure | Hard to calibrate |
| Proportional to variance | \(\Omega = \text{diag}(P\tau\Sigma P^\top)\) | Simple | No explicit confidence level |
| **Idzorek** | Mapped from % confidence | Intuitive & consistent | Requires a small numerical search |
| Satchell–Scowcroft | Alternative analytic form | Closed-form | Less widely used |

---

### 8. Summary

Idzorek’s method does **not** change the Black-Litterman formula itself.  
It only provides a disciplined and intuitive way to fill in the matrix \(\Omega\).

**Workflow when using Idzorek:**

1. Form your views (\(P\), \(Q\)).  
2. Assign a confidence percentage \(c_i\) to each view.  
3. Convert each \(c_i\) into the corresponding \(\omega_i\) (via search or approximation).  
4. Build \(\Omega = \text{diag}(\omega_1,\ldots,\omega_k)\).  
5. Run the standard Black-Litterman update and optimization.

This is currently one of the most popular practical implementations of Black-Litterman in the industry.

Below is a clean, self-contained implementation of the Black-Litterman model with Idzorek’s confidence-to-Ω mapping.

```python
"""
Black-Litterman with Idzorek’s Method
-------------------------------------
Converts user-specified confidence percentages into the view
uncertainty matrix Ω, then computes posterior returns and weights.
"""

import numpy as np
import pandas as pd
from scipy.optimize import minimize_scalar


def black_litterman(sigma, pi, p, q, omega, tau=0.05):
    """
    Classic Black-Litterman posterior expected returns.
    
    Parameters
    ----------
    sigma : (n, n) covariance matrix
    pi    : (n,)   equilibrium expected returns
    p     : (k, n) pick matrix
    q     : (k,)   view returns
    omega : (k, k) view uncertainty matrix
    tau   : float  prior uncertainty scaler
    
    Returns
    -------
    mu_bl : (n,) posterior expected returns
    """
    tau_sigma = tau * sigma
    # Middle term
    middle = p @ tau_sigma @ p.T + omega
    # BL formula
    mu_bl = pi + tau_sigma @ p.T @ np.linalg.solve(middle, (q - p @ pi))
    return mu_bl


def bl_weights(mu, sigma, risk_aversion=3.0, long_only=True):
    """
    Mean-variance weights from expected returns.
    Unconstrained solution + optional long-only projection.
    """
    w = np.linalg.solve(risk_aversion * sigma, mu)
    if long_only:
        w = np.maximum(w, 0.0)
        if w.sum() > 0:
            w = w / w.sum()
    return w


def idzorek_omega(
    sigma,
    pi,
    p,
    q,
    confidences,
    tau=0.05,
    risk_aversion=3.0,
    tol=1e-6,
):
    """
    Idzorek (2005) method: convert confidence percentages into Ω.
    
    Parameters
    ----------
    sigma        : (n, n) covariance matrix
    pi           : (n,)   equilibrium returns
    p            : (k, n) pick matrix
    q            : (k,)   view returns
    confidences  : (k,)   confidence in each view, in (0, 1]
    tau          : float
    risk_aversion: float  used to compute weights
    
    Returns
    -------
    omega : (k, k) diagonal uncertainty matrix
    """
    k = p.shape[0]
    n = sigma.shape[0]
    omega_diag = np.zeros(k)

    # Equilibrium weights (no views)
    w_eq = bl_weights(pi, sigma, risk_aversion)

    for i in range(k):
        c = float(np.clip(confidences[i], 1e-4, 1.0))

        # --- Weights when view i is 100% certain ---
        # Use a very small omega for this view only
        omega_certain = np.diag(np.ones(k) * 1e6)          # other views almost ignored
        omega_certain[i, i] = 1e-8                         # this view almost certain

        mu_certain = black_litterman(sigma, pi, p, q, omega_certain, tau)
        w_100 = bl_weights(mu_certain, sigma, risk_aversion)

        # Target weights according to Idzorek
        w_target = w_eq + c * (w_100 - w_eq)

        # --- Search for omega_i that produces w_target ---
        def objective(omega_i):
            omega_trial = np.diag(np.ones(k) * 1e6)
            omega_trial[i, i] = max(omega_i, 1e-12)
            mu_trial = black_litterman(sigma, pi, p, q, omega_trial, tau)
            w_trial = bl_weights(mu_trial, sigma, risk_aversion)
            return np.sum((w_trial - w_target) ** 2)

        # Bounded scalar search
        res = minimize_scalar(
            objective,
            bounds=(1e-12, 1e2),
            method="bounded",
            options={"xatol": tol},
        )
        omega_diag[i] = res.x

    return np.diag(omega_diag)


def black_litterman_idzorek(
    sigma,
    pi,
    p,
    q,
    confidences,
    tau=0.05,
    risk_aversion=3.0,
):
    """
    Full pipeline: Idzorek Ω → BL posterior returns → weights.
    
    Returns
    -------
    dict with mu_bl, omega, weights
    """
    omega = idzorek_omega(
        sigma, pi, p, q, confidences,
        tau=tau, risk_aversion=risk_aversion
    )
    mu_bl = black_litterman(sigma, pi, p, q, omega, tau=tau)
    weights = bl_weights(mu_bl, sigma, risk_aversion)

    return {
        "mu_bl": mu_bl,
        "omega": omega,
        "weights": weights,
        "omega_diag": np.diag(omega),
    }

# =========================================================
if __name__ == "__main__":
    np.set_printoptions(precision=4, suppress=True)

    # --- 3-asset toy example ---
    symbols = ["A", "B", "C"]
    # Covariance matrix (annualized)
    sigma = np.array([
        [0.0400, 0.0120, 0.0080],
        [0.0120, 0.0225, 0.0060],
        [0.0080, 0.0060, 0.0196],
    ])
    # Equilibrium returns (from reverse optimization or simply given)
    pi = np.array([0.06, 0.04, 0.05])

    # Two views:
    # View 1 (absolute): Asset A will return 9%
    # View 2 (relative): Asset B will outperform Asset C by 1.5%
    p = np.array([
```

3. A ready-to-use wrapper that takes your momentum candidates and outputs BL weights?**Idzorek Confidence Mapping Explained**

Idzorek’s confidence mapping is the procedure that converts a user’s intuitive **percentage confidence** in a view into the corresponding **diagonal element of the uncertainty matrix \(\Omega\)** used by the Black-Litterman model.

---

### 1. Why a Mapping Is Needed

In Black-Litterman we need the matrix \(\Omega\), which represents the uncertainty (variance) of each view.

Most investors cannot answer:
> “What is the variance of my view?”

But they can answer:
> “I am 70% confident in this view.”

Idzorek’s method provides a disciplined translation:

\[
\text{Confidence } c_i \in (0,1] \quad \longrightarrow \quad \omega_i = \Omega_{ii}
\]

---

### 2. Core Intuition

Consider two extreme portfolios for a given view \(i\):

| Case | Meaning | Portfolio Weights |
|------|---------|-------------------|
| No confidence (\(c_i = 0\)) | Ignore the view completely | Equilibrium weights \(w_{\text{eq}}\) |
| Full confidence (\(c_i = 1\)) | Treat the view as 100% certain | Weights \(w_{100}\) |

Idzorek assumes that at intermediate confidence \(c_i\), the **desired weights** should lie on the straight line between these two extremes:

\[
w_{\text{target}}(c_i) = w_{\text{eq}} + c_i \,(w_{100} - w_{\text{eq}})
\]

The mapping then finds the value of \(\omega_i\) that makes the Black-Litterman model produce weights as close as possible to \(w_{\text{target}}(c_i)\).

---

### 3. Step-by-Step Mapping Procedure

For each view \(i = 1,\dots,k\):

**Step 1 – Equilibrium weights**  
Compute the optimal weights using only the equilibrium returns \(\Pi\) (no views):

\[
w_{\text{eq}} = \arg\max_w \; w^\top\Pi - \frac{\lambda}{2}w^\top\Sigma w
\]

**Step 2 – 100% confidence weights**  
Temporarily set the uncertainty of view \(i\) to nearly zero (\(\omega_i \approx 0\)) and the uncertainty of all other views to a very large number.  
Run Black-Litterman and obtain weights \(w_{100}\).

**Step 3 – Target weights**  
\[
w_{\text{target}} = w_{\text{eq}} + c_i \,(w_{100} - w_{\text{eq}})
\]

**Step 4 – Solve for \(\omega_i\)**  
Find the scalar \(\omega_i > 0\) such that when Black-Litterman is run with that \(\omega_i\), the resulting weights \(w(\omega_i)\) are as close as possible to \(w_{\text{target}}\):

\[
\omega_i^* = \arg\min_{\omega_i > 0} \; \bigl\| w(\omega_i) - w_{\text{target}} \bigr\|^2
\]

This is a one-dimensional numerical search.

**Step 5 – Assemble \(\Omega\)**  
\[
\Omega = \text{diag}(\omega_1^*,\omega_2^*,\dots,\omega_k^*)
\]

---

### 4. Mathematical Relationship (Approximate Closed Form)

A widely used approximation that avoids numerical search is:

\[
\omega_i \approx \bigl(P_i\,(\tau\Sigma)\,P_i^\top\bigr) \cdot \frac{1-c_i}{c_i}
\]

Where:
- \(P_i\) is the \(i\)-th row of the pick matrix
- \(\tau\Sigma\) is the scaled prior covariance

**Behavior of the formula**
- \(c_i \to 1\) (full confidence) \(\Rightarrow \omega_i \to 0\) (view treated as certain)
- \(c_i \to 0\) (no confidence) \(\Rightarrow \omega_i \to \infty\) (view is ignored)
- \(c_i = 0.5\) \(\Rightarrow \omega_i\) equals the prior variance of the view portfolio

---

### 5. Visual Interpretation

```
c = 0.0          c = 0.5          c = 1.0
w = w_eq    →    w = midpoint  →  w = w_100
(ignore view)     (partial tilt)   (full view)
```

The mapping ensures that the strength of the tilt away from equilibrium is directly proportional to the stated confidence.

---

### 6. Important Properties

| Property | Explanation |
|----------|-------------|
| Monotonic | Higher confidence always produces a smaller \(\omega_i\) |
| View-specific | Each view has its own \(\omega_i\); views do not interfere |
| Scale-consistent | Confidence is expressed on a common 0–100% scale |
| Still Bayesian | The resulting \(\Omega\) is inserted into the original BL formula |

---

### 7. Practical Recommendations

1. Use confidences in the range **0.40 – 0.80**. Extremely high values (e.g. 0.95) often produce overly aggressive weights.
2. Relative views usually deserve higher confidence than absolute views.
3. When many views are present, be more conservative with the confidence levels to avoid over-tilting.
4. The numerical search version is more accurate; the closed-form approximation is faster and usually good enough for most applications.

---

### 8. Summary Formula Chain

\[
\begin{align*}
w_{\text{eq}} &= \text{MV}(\Pi,\Sigma)\\[6pt]
w_{100} &= \text{BL}(\omega_i\approx 0)\\[6pt]
w_{\text{target}} &= w_{\text{eq}} + c_i(w_{100}-w_{\text{eq}})\\[6pt]
\omega_i^* &= \arg\min_{\omega_i}\;\|w(\omega_i)-w_{\text{target}}\|^2\\[6pt]
\Omega &= \text{diag}(\omega_1^*,\dots,\omega_k^*)
\end{align*}
\]

This is the complete Idzorek confidence mapping.

Would you like me to also show a small numerical walk-through with real numbers (3 assets, 1–2 views) so you can see the weights and \(\omega_i\) change with different confidence levels?**Black-Litterman Model — Basics**

The Black-Litterman model is a portfolio construction method developed by Fischer Black and Robert Litterman (Goldman Sachs, early 1990s). It improves on classical Mean-Variance Optimization by combining two sources of information about expected returns in a consistent way.

---

### 1. The Problem It Solves

Traditional Mean-Variance Optimization (Markowitz) has well-known practical problems:

- Expected returns are very hard to estimate accurately.
- Small changes in expected returns can cause large swings in optimal weights.
- The optimizer often produces extreme or unintuitive portfolios (corner solutions).

Black-Litterman addresses these issues by starting from a neutral reference point (the market) and then tilting the portfolio according to the investor’s views, with the size of the tilt controlled by the investor’s confidence.

---

### 2. Core Idea

> Begin with the market equilibrium (what returns would make the current market-cap portfolio optimal).  
> Then blend in your own views, where more confident views have a stronger influence.

The result is a set of expected returns that are more stable and more intuitive than raw historical averages or pure subjective forecasts.

---

### 3. Main Components

| Component | Meaning |
|-----------|---------|
| **Equilibrium returns (\(\Pi\))** | Returns implied by current market-cap weights (reverse optimization) |
| **Investor views** | Your forecasts about absolute or relative performance of assets |
| **Confidence** | How strongly you believe each view (affects the uncertainty matrix \(\Omega\)) |
| **Covariance matrix (\(\Sigma\))** | Risk structure of the assets |
| **Posterior returns (\(\mu_{BL}\))** | The blended expected returns produced by the model |
| **Optimization** | Final step that turns \(\mu_{BL}\) into portfolio weights |

---

### 4. High-Level Process

```
1. Take market-cap weights
          ↓
2. Reverse-optimize to get equilibrium returns (Π)
          ↓
3. Express your views (absolute or relative)
          ↓
4. Specify confidence in each view
          ↓
5. Combine Π and views with a Bayesian formula
          ↓
6. Obtain posterior expected returns (μ_BL)
          ↓
7. Run mean-variance optimization → final weights
```

---

### 5. Types of Views

**Absolute view**  
“Asset A will return 8%.”

**Relative view**  
“Asset A will outperform Asset B by 2%.”  
(This form is usually more reliable and more commonly used.)

Views are written in matrix form as:

\[
P\mu = Q + \text{error}
\]

- \(P\) selects the assets involved in each view  
- \(Q\) contains the expected excess returns of those views

---

### 6. Key Intuition of the Blending

The model produces expected returns that lie between:

- Pure market equilibrium (if you have no confidence in your views)
- Your views (if you are extremely confident)

The higher your confidence, the closer the final expected returns (and therefore the weights) move toward your views.

---

### 7. Why It Is Popular

- Avoids extreme portfolios that pure Markowitz often produces  
- Gives a clear way to incorporate research / signals / opinions  
- Starts from a neutral, observable reference point (the market)  
- Separates “what I think” from “how sure I am”  
- Widely used in both quantitative and discretionary asset-management processes

---

### 8. Simple Analogy

Think of the market portfolio as the default recommendation.  
Black-Litterman lets you say:

> “I mostly agree with the market, but I have a few opinions.  
> Please tilt the portfolio in the direction of my opinions,  
> and the strength of the tilt should match how confident I am.”

---

### 9. What Black-Litterman Does *Not* Do

- It does not eliminate the need for a good covariance matrix  
- It does not automatically generate views (you or a model must supply them)  
- It is not a pure risk-based method like Risk Parity or HRP  
- The quality of the output still depends on the quality of the views and the confidence levels you assign

---

### 10. One-Sentence Summary

**Black-Litterman = Market equilibrium + Investor views, blended according to confidence, then optimized.**

(เช่น Calibration system, Meta-label decision rule, หรือ Decision policy ที่แม่นยำขึ้น)**CPCV Validation Method Explained**  
**(Combinatorial Purged Cross-Validation)**

CPCV is a rigorous validation technique designed specifically for financial machine learning. It was popularized by Marcos López de Prado in *Advances in Financial Machine Learning*. It addresses the major flaws of ordinary cross-validation when dealing with time-series financial data.

---

### 1. Why Ordinary Cross-Validation Fails in Finance

Standard K-Fold or even simple walk-forward validation suffers from three critical problems:

| Problem | Description | Consequence |
|---------|-------------|-------------|
| **Data leakage** | Future information leaks into the training set through overlapping labels | Performance looks artificially good |
| **Overlapping outcomes** | Labels (e.g., 10-day forward returns) overlap between train and test | Observations are not independent |
| **Single path dependence** | Only one or a few train/test splits are tested | Results can be driven by luck in a particular period |

CPCV is built to mitigate all three.

---

### 2. Core Components of CPCV

CPCV combines three ideas:

### A. Purging
When a test observation uses information up to time \(t\) and a label that extends to \(t + h\) (the holding period or forecast horizon), any training observation whose label overlaps with this interval must be removed.

```
Training data     Purge zone      Test data
[---------------|XXXXXXXXXX|===============]
                ← horizon →
```

### B. Embargo (optional but recommended)
An additional buffer after the test set is also removed to reduce the effect of serial correlation.

### C. Combinatorial Splits
Instead of using only one way to split the data, CPCV divides the timeline into \(N\) groups and selects every possible combination of \(k\) groups as the test set.

Number of paths = \(\binom{N}{k}\)

Example:  
- 6 groups, choose 2 for testing → \(\binom{6}{2} = 15\) different train/test paths

This produces a **distribution of results** rather than a single number.

---

### 3. Step-by-Step CPCV Validation Process

1. **Sort all data chronologically**
2. **Divide the time axis into \(N\) sequential groups** of roughly equal size
3. **Generate all combinations** of \(k\) groups to serve as test sets
4. For each combination:
   - Define the test set
   - Apply purging (and embargo) to remove overlapping training observations
   - Train the model on the remaining data
   - Predict on the test set
   - Record performance metrics
5. **Aggregate results** across all paths (mean, standard deviation, percentage of profitable paths, etc.)

---

### 4. What CPCV Actually Validates

Typical metrics collected across paths:

- Accuracy / Hit rate
- AUC
- Log-loss
- Average return of predicted positives vs predicted negatives (economic value)
- Percentage of paths that exceed a performance threshold
- Stability of feature importance (optional)

The most important output is not the average score, but the **distribution and consistency** of the score across many different time periods.

---

### 5. Why CPCV Is Considered Stronger Validation

| Feature | Ordinary CV | Walk-Forward | CPCV |
|---------|-------------|--------------|------|
| Prevents label leakage | Weak | Partial | Strong (purging) |
| Tests multiple market regimes | Limited | Moderate | Strong (many combinations) |
| Produces performance distribution | No | Limited | Yes |
| Controls for multiple-testing bias | No | No | Better |
| Suitable for small financial datasets | Poor | Acceptable | Good |

---

### 6. Practical Illustration

Suppose you have 6 years of daily data and use a 10-day forecast horizon.

- Split into 6 annual groups
- Choose every combination of 2 groups as test → 15 paths
- For each path, purge any training observations whose 10-day label overlaps the test period
- Train → test → record results

You then see, for example:
- Mean hit rate: 0.56
- Standard deviation across paths: 0.04
- 12 out of 15 paths > 0.53
- Average long-short return gap: +1.4%

This gives far more confidence than a single backtest or a single walk-forward run.

---

### 7. Limitations

- Computationally heavier than simple walk-forward
- Requires enough history to create meaningful groups
- Still depends on the quality of the features and labels
- Does not completely eliminate regime-shift risk
- Purging reduces training data size, which can hurt very data-hungry models

---

### 8. Summary

**CPCV = Purged Cross-Validation + Combinatorial evaluation of many train/test paths**

It answers a more realistic question than ordinary validation:

> “If I train on past data without leaking future information,  
> and I test across many different historical periods,  
> how consistently does this model perform?”

That consistency is what makes CPCV one of the most credible validation methods currently used in quantitative finance.

Combinatorial Purged Cross-Validation is an advanced validation technique for financial machine learning models. It was introduced to overcome the serious shortcomings of standard cross-validation when working with time-series financial data.

---

### 1. Purpose

CPCV answers a more realistic question than ordinary backtests or simple walk-forward validation:

> How well does the model perform across many different historical periods,  
> while strictly preventing future information from leaking into the training data?

It produces a **distribution of out-of-sample results** rather than a single performance number.

---

### 2. The Three Building Blocks

### A. Purging
Financial labels usually span a time interval (for example, a 10-day forward return).  
If a test observation uses information up to time \(t\) and its label ends at \(t+h\), then any training observation whose label overlaps this interval must be removed.

This prevents the model from indirectly seeing future outcomes during training.

### B. Embargo (commonly used together with purging)
An extra buffer zone immediately after the test period is also excluded from training. This further reduces the impact of serial correlation.

### C. Combinatorial Splits
The timeline is divided into \(N\) sequential groups.  
Every possible combination of \(k\) groups is selected as a test set.

Number of validation paths = \(\displaystyle\binom{N}{k}\)

Example:  
- 6 groups, test on 2 groups at a time → 15 different train/test paths.

Each path trains the model on the remaining data (after purging) and evaluates it on the chosen test groups.

---

### 3. Step-by-Step Process

1. Order all observations chronologically.
2. Split the time axis into \(N\) contiguous groups of roughly equal size.
3. Generate all combinations of \(k\) groups to serve as test sets.
4. For each combination:
   - Form the test set.
   - Remove from the training set any observations that overlap with the test labels (purging) and apply embargo if desired.
   - Train the model on the cleaned training set.
   - Generate predictions on the test set.
   - Record performance metrics.
5. Aggregate the results across all paths (mean, standard deviation, percentage of successful paths, economic metrics, etc.).

---

### 4. Why the Combinatorial Aspect Matters

A single train/test split (or even a standard walk-forward) can be lucky or unlucky depending on the particular period chosen.

By evaluating **every combination**, CPCV shows:

- How stable the performance is across different market regimes
- Whether good results are concentrated in only a few periods
- The typical range of outcomes you might expect

This makes the validation far more informative than a single backtest number.

---

### 5. Typical Metrics Reported

- Average accuracy / hit rate across paths
- Standard deviation of performance across paths
- Percentage of paths that exceed a minimum threshold
- Average return of predicted positive class vs negative class (economic value)
- Distribution of Sharpe ratios or other risk-adjusted metrics

The distribution and consistency of results are usually more important than the mean alone.

---

### 6. Comparison with Other Validation Methods

| Method | Prevents Leakage | Multiple Periods | Performance Distribution | Suitable for Finance |
|--------|------------------|------------------|---------------------------|----------------------|
| Standard K-Fold | Poor | Artificial | No | No |
| Simple Walk-Forward | Partial | Limited | Limited | Acceptable |
| Purged CV (single path) | Good | Limited | No | Good |
| **Combinatorial Purged CV** | Strong | Strong | Yes | Excellent |

---

### 7. Advantages

- Strong protection against label leakage
- Tests the model under many different historical conditions
- Produces a distribution of outcomes instead of a point estimate
- Reduces the risk of being fooled by a single lucky period
- Particularly useful when validating meta-labeling models, secondary models, or any predictive layer used for position sizing

---

### 8. Limitations

- More computationally expensive than simple walk-forward
- Requires sufficient history to form meaningful groups
- Purging reduces the amount of training data available for each path
- Does not eliminate the fundamental problem of changing market regimes
- Still depends on the quality of features and the economic meaningfulness of the labels

---

### 9. Summary

**Combinatorial Purged Cross-Validation = Purging (to stop leakage) + Combinatorial evaluation of many train/test paths**

It is currently one of the most rigorous and widely respected validation methods in quantitative finance for assessing whether a model has genuine, stable predictive power rather than fitting noise in a particular historical period.

When using Purged Cross-Validation or Combinatorial Purged Cross-Validation (CPCV), several key parameters control how the data is split, how leakage is prevented, and how thorough the validation is. Choosing them well is critical for reliable results.

---

### 1. Main Parameters

| Parameter | Meaning | Typical Role |
|-----------|---------|--------------|
| **\(N\)** (n_groups) | Number of sequential time groups the data is divided into | Controls granularity of splits |
| **\(k\)** (n_test_groups) | Number of groups used as the test set in each path | Controls test-set size and number of combinations |
| **Purge length** (horizon) | Number of bars/days removed around the test set to prevent label overlap | Prevents leakage from overlapping labels |
| **Embargo** | Extra buffer (usually after the test set) that is also excluded from training | Further reduces serial-correlation leakage |
| **Label horizon (\(h\))** | The length of the forward-looking label (e.g., 5-day or 10-day return) | Determines the minimum purge length |

---

### 2. Detailed Explanation of Each Parameter

### \(N\) — Number of Groups
- The entire time series is split into \(N\) contiguous, roughly equal-sized groups.
- Larger \(N\) → finer splits, more combinations possible, but each training set becomes smaller.
- Smaller \(N\) → coarser splits, fewer combinations, larger training sets.

**Common choices**: 5 to 10 groups for daily data spanning several years.

### \(k\) — Number of Test Groups
- In each validation path, \(k\) of the \(N\) groups are held out as the test set.
- The number of total paths is the combination \(\binom{N}{k}\).

Examples:
- \(N=6\), \(k=1\) → 6 paths (similar to classic walk-forward)
- \(N=6\), \(k=2\) → 15 paths
- \(N=8\), \(k=2\) → 28 paths

Higher \(k\) makes each test set larger and the validation more stringent, but reduces training data more aggressively.

### Purge Length
This is the most important leakage-prevention parameter.

If your label looks forward \(h\) days (e.g., 10-day return), then any training observation whose label overlaps the test period must be removed.  
The purge window is therefore at least \(h\) bars before (and sometimes after) the test set.

**Rule of thumb**:
\[
\text{Purge length} \ge \text{label horizon } h
\]

### Embargo
An additional number of bars (often also around \(h\) or a fraction of \(h\)) that are excluded after the test set.  
It helps when returns or features have lingering autocorrelation.

Many practical implementations set:
- Purge = \(h\)
- Embargo = \(h\) or \(0.5h\)

### Label Horizon (\(h\))
This is not a CV tuning parameter per se, but it directly determines how large the purge (and usually the embargo) must be.  
It is fixed by the prediction task (e.g., “Will this signal be profitable over the next 10 days?”).

---

### 3. How the Parameters Interact

```
Total paths = C(N, k) = N! / (k!(N-k)!)

Training data size per path ≈ (N - k)/N of total data
                              minus the purged and embargoed observations
```

Trade-offs:

| Goal | Suggested Direction |
|------|---------------------|
| More stable performance estimate | Increase \(N\) and/or \(k\) (more paths) |
| Larger training sets | Decrease \(k\) or decrease \(N\) |
| Stronger leakage protection | Increase purge and embargo (at least = label horizon) |
| Faster computation | Decrease \(N\) or \(k\) |

---

### 4. Practical Recommendations

**For daily equity strategies (typical case)**

| Situation | Recommended Starting Point |
|-----------|---------------------------|
| 3–6 years of data, label horizon 5–10 days | \(N = 6\), \(k = 2\), purge = 10, embargo = 5–10 |
| Longer history (8+ years) | \(N = 8\)–10, \(k = 2\) |
| Very short history | \(N = 5\), \(k = 1\) (closer to purged walk-forward) |
| Meta-labeling / secondary models | Same as above; often \(k = 2\) is preferred |

**General rules**
- Never set purge length shorter than the label horizon.
- Prefer more paths over a single optimistic split.
- Monitor both the **mean** and the **dispersion** of results across paths.
- If many paths produce near-zero or negative economic value, the signal is likely weak or unstable.

---

### 5. Example

- Data: 6 years of daily bars  
- Label: 10-day forward return → \(h = 10\)  
- Settings: \(N = 6\), \(k = 2\), purge = 10, embargo = 5  

Result:
- 15 different train/test paths
- Each test set ≈ 1/3 of the data (2 out of 6 groups)
- Training set is the remaining 4 groups after removing overlapping labels and the embargo zone

This configuration is a common, well-balanced choice for many equity momentum and meta-labeling studies.

---

### 6. Summary Table

| Parameter | Controls | Typical Range | Critical Constraint |
|-----------|----------|---------------|---------------------|
| \(N\) | Number of time blocks | 5–10 | Enough data per group |
| \(k\) | Test-set size & number of paths | 1–3 | \(k < N/2\) usually |
| Purge | Leakage from overlapping labels | ≥ label horizon | Must be ≥ \(h\) |
| Embargo | Residual serial correlation | 0 to \(h\) | Optional but recommended |
| Label horizon \(h\) | Forecast period | Strategy-dependent | Fixed by the problem |

---

Correct parameter choices do not magically create edge, but incorrect choices (especially insufficient purging) can easily create the *illusion* of edge. That is why understanding these parameters is essential for credible validation.

Would you like recommended parameter sets for different holding periods (e.g., 5-day vs 20-day labels), or guidance on interpreting the distribution of CPCV results?**CPCV Combinatorial Paths Explained**

In Combinatorial Purged Cross-Validation (CPCV), a **path** is one complete train-and-test cycle. The “combinatorial” part refers to how these paths are systematically generated by selecting different combinations of time groups as the test set.

---

### 1. Basic Setup

1. The full time series is divided into \(N\) sequential, non-overlapping groups (blocks of time).
2. In each path, we choose \(k\) of those groups to serve as the **test set**.
3. The remaining groups (after purging and embargo) become the **training set**.
4. Every unique way of choosing \(k\) groups out of \(N\) creates one path.

The total number of paths is the binomial coefficient:

\[
\text{Number of paths} = \binom{N}{k} = \frac{N!}{k!(N-k)!}
\]

---

### 2. Concrete Example

Suppose:
- \(N = 6\) groups (Group 0 to Group 5)
- \(k = 2\) (each path uses 2 groups as test)

Then the number of paths is:

\[
\binom{6}{2} = 15
\]

Here are some of the 15 paths:

| Path | Test Groups | Training Groups (before purging) |
|------|-------------|----------------------------------|
| 1    | 0, 1        | 2, 3, 4, 5                       |
| 2    | 0, 2        | 1, 3, 4, 5                       |
| 3    | 0, 3        | 1, 2, 4, 5                       |
| 4    | 0, 4        | 1, 2, 3, 5                       |
| 5    | 0, 5        | 1, 2, 3, 4                       |
| 6    | 1, 2        | 0, 3, 4, 5                       |
| ...  | ...         | ...                              |
| 15   | 4, 5        | 0, 1, 2, 3                       |

Each row is one full validation path: train on the allowed data, test on the selected groups, and record the performance.

---

### 3. What Happens Inside One Path

For any single path:

1. Identify the test groups.
2. Apply **purging**: remove from the training data any observations whose labels overlap the test period.
3. Apply **embargo** (optional but recommended): remove an extra buffer after the test period.
4. Train the model on the cleaned training set.
5. Predict on the test groups.
6. Store the performance metrics for that path.

Because this process is repeated for every combination, you obtain a **distribution** of results instead of a single number.

---

### 4. Why Combinatorial Paths Matter

| Benefit | Explanation |
|---------|-------------|
| Reduces path dependence | Performance is not tied to one arbitrary train/test split |
| Tests many regimes | Different combinations cover different historical periods |
| Shows stability | You can see whether good results appear in most paths or only in a few lucky ones |
| Better statistical picture | Mean, standard deviation, and percentage of successful paths become meaningful |

A model that performs well on 13 out of 15 paths is far more credible than one that performs well on only a single walk-forward split.

---

### 5. Visual Illustration (N = 6, k = 2)

```
Time groups:  [ 0 | 1 | 2 | 3 | 4 | 5 ]

Path 1 test:  [ T | T |   |   |   |   ]
Path 2 test:  [ T |   | T |   |   |   ]
Path 3 test:  [ T |   |   | T |   |   ]
...
Path 15 test: [   |   |   |   | T | T ]
```

Each “T” marks the groups held out for testing in that path. The remaining groups (after purging) are used for training.

---

### 6. Effect of Changing N and k

| Settings | Number of Paths | Test Set Size | Training Set Size | Character |
|----------|------------------|---------------|-------------------|-----------|
| N=6, k=1 | 6               | Small         | Large             | Closer to classic walk-forward |
| N=6, k=2 | 15              | Medium        | Medium            | Common balanced choice |
| N=8, k=2 | 28              | Medium        | Larger history needed | More thorough |
| N=6, k=3 | 20              | Large         | Smaller           | Stricter test |

---

### 7. Key Takeaway

A **combinatorial path** in CPCV is one unique way of selecting \(k\) time groups as the test set (with the rest used for training after purging).  

By evaluating **all** such combinations, CPCV delivers a robust distribution of out-of-sample performance, making it much harder for a model to look good simply because of a lucky historical period.

Purging is the step that prevents label leakage. It removes training observations whose labels overlap in time with the test period. Below is a clear explanation of how it works inside each combinatorial path.

---

### 1. Why Purging Is Required

Most financial labels are **forward-looking** and span a period of time.

Example:  
Label = 10-day forward return  
→ The label for day \(t\) uses information from day \(t\) to day \(t+10\).

If a test observation is on day 100, its label depends on days 100–110.  
Any training observation whose own label also touches days 100–110 would leak future information. Those training observations must be removed.

---

### 2. Basic Timeline Illustration

Assume:
- Label horizon \(h = 10\) days
- One path has a test set that runs from day 100 to day 130

```
Time axis:
... 80    90        100         110        120        130        140 ...
     |     |         |           |          |          |          |
```

Test period: days 100–130  
Label horizon: 10 days

**Purge zone** (must be excluded from training):
- Before the test set: roughly days 90–99 (because labels starting in this range would extend into the test period)
- Sometimes a symmetric purge after the test set is also applied

```
Training allowed          PURGE ZONE          TEST SET          (possible embargo)
[----------------------|XXXXXXXXXXXXXXX|=====================|xxxxxxxxxx|------------]
                       ↑               ↑                     ↑
                     ~90             100                   130
```

Any observation whose label interval overlaps the test interval is purged.

---

### 3. Precise Purging Rule

For a test set covering times \([t_{\text{start}}, t_{\text{end}}]\):

An observation at time \(t\) (with label horizon \(h\)) must be **purged** from training if its label interval overlaps the test interval, i.e.:

\[
[t,\ t+h]\ \cap\ [t_{\text{start}},\ t_{\text{end}}]\ \neq\ \emptyset
\]

This is equivalent to removing training points that satisfy:

\[
t \in (t_{\text{start}} - h,\ t_{\text{end}})
\]

(plus any additional embargo buffer you choose to apply).

---

### 4. Purging Inside a Full Combinatorial Path

Example settings:
- 6 time groups (G0 … G5)
- Path test groups = G2 and G3
- Label horizon \(h = 10\) days

**Step-by-step for this path:**

1. **Test set** = all observations belonging to G2 ∪ G3
2. Determine the earliest and latest timestamps in the test set
3. Compute the purge window:  
   \([t_{\text{test start}} - h,\ t_{\text{test end}}]\)
4. Remove from the training set (G0 + G1 + G4 + G5) every observation that falls inside the purge window
5. (Optional) Apply embargo: remove a few extra days immediately after the test set
6. Train only on the remaining observations
7. Evaluate on the pure test set (G2 ∪ G3)

The same logic is applied independently to every combinatorial path.

---

### 5. Visual Example with Groups

```
Groups:     G0      G1      G2      G3      G4      G5
            |-------|-------|-------|-------|-------|-------|

Test path:                  [TEST ] [TEST ]
                            G2      G3

Purge zone (h = 10 days):
                     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
                     (extends h days before G2 and covers through end of G3)
```

Training data that survives = (G0 + G1 + G4 + G5) minus any bars that sit inside the purge zone.

---

### 6. What Gets Removed vs What Stays

| Observation time | Label ends at | Overlaps test? | Action |
|------------------|---------------|----------------|--------|
| Well before test start − h | Before test | No | Keep for training |
| Inside (test start − h) to test end | Overlaps test | Yes | **Purge** |
| After test end (+ embargo) | After test | No | Keep for training |

---

### 7. Common Practical Choices

| Item | Typical Setting |
|------|------------------|
| Label horizon \(h\) | Determined by the strategy (e.g. 5, 10, 20 days) |
| Purge length | ≥ \(h\) |
| Embargo | 0 to \(h\) days after the test set |
| Symmetric purge | Sometimes also purge a short window after the test set |

---

### 8. Key Takeaway

Purging guarantees that **no training label is allowed to “see” any part of the test period**.  

Without it, the model can indirectly learn from future outcomes and produce optimistically biased validation results. When purging is applied correctly inside every combinatorial path, the performance numbers become much more credible.

### 1. Meta-Labeling คืออะไร (สรุปสั้น)

**Primary Model / Primary Signal**  
→ สร้างสัญญาณซื้อ-ขาย (ในระบบเรา = ติด ≥ k timeframe)

**Meta-Model**  
→ รับสัญญาณจาก Primary แล้วทำนายว่า “สัญญาณนี้จะสำเร็จหรือไม่”  
→ ผลลัพธ์มักเป็น probability หรือ binary (take / skip)  
→ ใช้เพื่อกรองสัญญาณหรือปรับขนาดตำแหน่ง (sizing) เท่านั้น **ไม่สร้างสัญญาณเอง**

Label ของ Meta-Model มักเป็น:
- 1 = สัญญาณ Primary ได้กำไร (หรือชนะ benchmark) ในช่วง holding period
- 0 = สัญญาณ Primary ขาดทุนหรือไม่ดีพอ

---

### 2. ทำไม Meta-Labeling ต้องใช้ CPCV เป็นพิเศษ

Meta-Labeling มีลักษณะที่ทำให้ validation ธรรมดาอันตราย:

| ปัญหา | ผลกระทบ |
|------|--------|
| Label ซ้อนทับกันสูง | ข้อมูล train/test ไม่อิสระ |
| Sample ถูกกรองแล้ว (เฉพาะวันที่ Primary เกิดสัญญาณ) | ข้อมูลน้อยลง + selection bias |
| ใช้เพื่อ sizing | Overfit นิดเดียวก็ทำให้จัดขนาดผิดพลาดหนัก |
| มักมีหลายฟีเจอร์ | Multiple testing รุนแรง |

CPCV ช่วยแก้ได้ตรงจุดเพราะ:
- **Purging** ป้องกัน leakage จาก label ที่ซ้อนทับ
- **Combinatorial paths** แสดงความเสถียรข้ามหลายช่วงเวลา
- ให้ภาพการกระจายของผลลัพธ์ ไม่ใช่แค่ตัวเลขเดียว

---

### 3. โครงสร้างข้อมูลใน Meta-Labeling + CPCV

สมมติ Primary Signal เกิดในวันที่ \( t \):

- Features (X): ค่าต่าง ๆ ณ วันที่ \( t \) หรือก่อนหน้านั้น  
  (n_tf, streak, residual momentum, volume surge, regime features ฯลฯ)
- Label (y): ผลลัพธ์ของสัญญาณในช่วง \( [t+1, t+h] \)  
  เช่น  
  - 1 ถ้า forward return > 0 (หรือ > median ของวันนั้น)  
  - 0 ถ้าไม่ใช่

จุดสำคัญ:  
Label ของ meta-model **กินเวลาข้างหน้า h วัน** → ต้อง purge ตาม h

### 4. กลไก CPCV เมื่อใช้กับ Meta-Labeling

### ขั้นตอนหลัก

1. **สร้าง Meta-Dataset**  
   เอาเฉพาะวันที่ Primary Signal เกิด → ได้ตาราง (features, label)

2. **แบ่งเวลาเป็น N กลุ่ม**  
   ตามปฏิทิน (ไม่สุ่ม) เพื่อรักษาลำดับเวลา

3. **สร้าง Combinatorial Paths**  
   เลือกทุก combination ของ k กลุ่มเป็น test set

4. **ในแต่ละ Path**
   - กำหนด test set = สัญญาณที่เกิดในกลุ่มทดสอบ
   - **Purge**: ลบข้อมูล train ที่ label ไปซ้อนกับช่วง test
   - Train Meta-Model เฉพาะบนข้อมูลที่เหลือ
   - ทำนายบน test set
   - บันทึกผล

5. **สรุปผลข้ามทุก Path**

---

### 5. Purging ในบริบท Meta-Labeling (สำคัญมาก)

สมมติ holding period / label horizon = 10 วัน

ถ้า test path มีสัญญาณวันที่ 100–130:

- Label ของสัญญาณวันที่ 100 จะใช้ข้อมูลถึงวัน 110
- Label ของสัญญาณวันที่ 95 จะใช้ข้อมูลถึงวัน 105 → **ซ้อนกับ test** → ต้องถูก purge

กฎทั่วไป:

```
ลบข้อมูล train ใดก็ตามที่ช่วง label ของมัน
ไปทับกับช่วงเวลาของ test set
```

ถ้าไม่ทำขั้นตอนนี้ Meta-Model จะ “แอบเห็น” อนาคตและดูแม่นเกินจริง

### 6. เมตริกที่ควรดูใน Meta-Labeling + CPCV

| เมตริก | ความหมาย |
|------|---------|
| Mean Hit Rate / Accuracy | ทายถูกมากน้อยแค่ไหนโดยเฉลี่ย |
| Std ของ Hit Rate ข้าม paths | เสถียรไหม |
| % Paths ที่ Hit > 0.55 | มี edge สม่ำเสมอหรือโชค |
| AUC เฉลี่ย | แยกดี-แย่ได้ดีแค่ไหน |
| Long-Short / Take-Skip gap | มูลค่าทางเศรษฐกิจจริง |
| Calibration | conf 0.7 แล้วชนะจริงประมาณ 70% ไหม |

**จุดตัดสินใจสำคัญ**:  
ถ้า Meta-Model ผ่าน CPCV แล้ว Long-Short gap ยังเป็นบวกหลังต้นทุน → มีสิทธิ์เอาไปใช้ sizing  
ถ้าไม่ผ่าน → ปิด meta-sizing แล้วกลับไปใช้ Primary Signal อย่างเดียว

```
Paths           : 15
```

### 8. จุดที่คนมักพลาดเมื่อใช้ CPCV กับ Meta-Labeling

1. ลืม purge ตาม label horizon  
2. ใช้ accuracy อย่างเดียวโดยไม่ดู economic gap  
3. ให้ Meta-Model สร้างสัญญาณเองแทนที่จะแค่กรอง  
4. ใช้ข้อมูลน้อยเกินไปจน combinatorial paths ไม่มีความหมาย  
5. Tune ฟีเจอร์และ threshold หลายรอบโดยไม่มี pre-registration

นี่คือวิธีที่ใช้ Meta-Labeling อย่างมีวินัยและใกล้เคียงมาตรฐานสถาบันมากที่สุด

1. **สร้าง candidate list** จากกลุ่ม A–E

### 8. สรุปหลักคิดสำคัญ

- Meta-Model ต้องการ features ที่บอก **คุณภาพของสัญญาณ** ไม่ใช่แค่แรงของราคา  
- Signal strength + Momentum quality + Volume confirmation + Regime คือแกนหลัก  
- น้อยแต่มั่นคง ดีกว่าเยอะแต่ไม่เสถียร  
- ทุกครั้งที่เพิ่ม feature ต้องผ่านการทดสอบแบบ purged/CPCV  
- เป้าหมายสุดท้ายคือทำให้ Meta-Model ช่วย “ไม่เล่นสัญญาณแย่” มากกว่าการไปหาสัญญาณใหม่

---

ต้องการให้ผมช่วยต่อในส่วนไหนเป็นพิเศษไหมครับ?

1. จัดลำดับความสำคัญของ features ที่มีในระบบปัจจุบัน  
2. วิธีทดสอบ feature importance แบบ purged  
3. ออกแบบชุด features เฉพาะสำหรับ holding period 8–12 วันของตลาดไทย
**ทดสอบ Feature Importance แบบ Purged**

ในงาน Meta-Labeling บนข้อมูลการเงิน **ห้ามใช้** feature importance แบบ ordinary (เช่น train_test_split ธรรมดา หรือ K-Fold ปกติ) เพราะจะมี leakage และให้ความสำคัญกับ feature ผิดตัว

วิธีที่ถูกต้องคือต้องวัดความสำคัญของ feature **ภายใต้เงื่อนไขที่มีการ purge** และ ideally ข้ามหลาย combinatorial paths

---

### 1. แนวทางที่แนะนำ (จากง่าย → เข้มงวด)

| วิธี | ความเข้มงวด | คำอธิบายสั้น |
|------|-------------|-------------|
| **Purged Single-Feature AUC / Hit** | ปานกลาง | ทดสอบทีละ feature แบบ univariate ภายใต้ purged split |
| **Purged Permutation Importance** | สูง | สุ่มสลาย feature แล้ววัดว่า performance ตกแค่ไหน (ใช้ CPCV paths) |
| **Leave-One-Feature-Out (LOFO) with CPCV** | สูงมาก | เทรนโมเดลโดยตัดทีละ feature แล้วเปรียบเทียบผลข้าม paths |
| **Group / Cluster Importance** | สูง | วัดเป็นกลุ่ม feature ที่ correlate กัน |

สำหรับระบบของคุณ แนะนำเริ่มจาก **Purged Permutation Importance บน CPCV paths** เพราะสมดุลระหว่างความถูกต้องกับความซับซ้อน

---

### 2. หลักการของ Purged Permutation Importance

1. รัน CPCV ตามปกติ → ได้ performance พื้นฐานของโมเดลเต็มชุด features
2. สำหรับแต่ละ feature:
   - ใน **test set ของแต่ละ path** ให้สุ่มสลายค่าของ feature นั้น (permute)
   - วัด performance ใหม่
   - ความสำคัญ = ผลที่ลดลงเมื่อ feature นั้นถูกทำลาย
3. เฉลี่ยความสำคัญข้ามทุก paths

ยิ่ง performance ตกมากเมื่อถูก permute ยิ่งแสดงว่า feature นั้นสำคัญจริง

---

### 3. โค้ดตัวอย่าง (พร้อมใช้กับระบบคุณ)

```python
"""
research/feature_importance_purged.py
Purged Permutation Importance for Meta-Labeling
"""

import numpy as np
import pandas as pd
from sklearn.linear_model import LogisticRegression
from sklearn.preprocessing import StandardScaler
from sklearn.metrics import roc_auc_score, accuracy_score

from research.advanced_features import build_advanced_panel
from research.cpcv import cpcv_splits, CORE_FEATS


def purged_permutation_importance(
    n_groups: int = 6,
    n_test_groups: int = 2,
    hold: int = 10,
    n_repeats: int = 5,
    random_state: int = 42,
):
    """
    คืน DataFrame สรุป importance ของแต่ละ feature
    """
    panel = build_advanced_panel(hold=hold)
    feats = [f for f in CORE_FEATS if f in panel.columns]
    panel = panel.dropna(subset=feats + ["y"]).copy()
    dates = sorted(panel["date"].unique())

    rng = np.random.default_rng(random_state)
    records = []

    for tr_dates, te_dates in cpcv_splits(dates, n_groups, n_test_groups, purge=hold):
        tr = panel[panel.date.isin(tr_dates)]
        te = panel[panel.date.isin(te_dates)]
        if len(tr) < 80 or len(te) < 20:
            continue

        scaler = StandardScaler().fit(tr[feats])
        X_tr = scaler.transform(tr[feats])
        X_te = scaler.transform(te[feats])
        y_tr = tr["y"].values
        y_te = te["y"].values

        model = LogisticRegression(max_iter=2000, C=0.5, class_weight="balanced")
        model.fit(X_tr, y_tr)

        # Baseline
        p_base = model.predict_proba(X_te)[:, 1]
        try:
            auc_base = roc_auc_score(y_te, p_base)
        except Exception:
            auc_base = np.nan
        hit_base = accuracy_score(y_te, (p_base >= 0.5).astype(int))

        # Permute each feature
        for j, feat in enumerate(feats):
            drops = []
            for _ in range(n_repeats):
                X_te_perm = X_te.copy()
                # permute column j
                X_te_perm[:, j] = rng.permutation(X_te_perm[:, j])
                p_perm = model.predict_proba(X_te_perm)[:, 1]
                try:
                    auc_perm = roc_auc_score(y_te, p_perm)
                except Exception:
                    auc_perm = np.nan
                drops.append(auc_base - auc_perm)

            records.append({
                "feature": feat,
                "auc_drop": np.nanmean(drops),
                "hit_base": hit_base,
                "auc_base": auc_base,
                "n_te": len(te),
            })

    df = pd.DataFrame(records)
    if df.empty:
        print("ไม่เพียงพอที่จะคำนวณ importance")
        return df

    summary = (
        df.groupby("feature")["auc_drop"]
        .agg(mean_auc_drop="mean", std_auc_drop="std", n_paths="count")
        .sort_values("mean_auc_drop", ascending=False)
    )
    summary["mean_auc_drop"] = summary["mean_auc_drop"].round(4)
    summary["std_auc_drop"] = summary["std_auc_drop"].round(4)

    print("=" * 60)
    print("PURGED PERMUTATION IMPORTANCE (AUC drop)")
    print("ค่าสูง = feature สำคัญ (เมื่อถูกทำลายแล้วโมเดลแย่ลงชัด)")
    print("=" * 60)
    print(summary)
    print("=" * 60)
    return summary


if __name__ == "__main__":
    purged_permutation_importance()
```

### 4. วิธีอ่านผล

| ผลลัพธ์ | ความหมาย |
|--------|---------|
| `mean_auc_drop` สูง | Feature สำคัญมาก |
| `mean_auc_drop` ใกล้ 0 | Feature แทบไม่มีประโยชน์ |
| `mean_auc_drop` ติดลบ | เมื่อเอาออกแล้วโมเดลดีขึ้น (น่าตัดทิ้ง) |
| `std_auc_drop` สูง | ความสำคัญไม่เสถียรข้ามช่วงเวลา |

**กฎง่าย ๆ**
- เก็บ feature ที่ `mean_auc_drop` สูงและเสถียร
- ตัด feature ที่ค่าใกล้ 0 หรือติดลบอย่างสม่ำเสมอ
- ระวัง feature ที่สำคัญแค่บาง paths (std สูง)

### 5. วิธีเสริมที่แนะนำให้ทำคู่กัน

1. **Correlation กับ label แบบง่าย** (ดูทิศทางเบื้องต้น)  
2. **Purged Permutation Importance** (ตัวหลัก)  
3. **Leave-One-Feature-Out** กับชุด features ที่เหลือหลังคัดแล้ว  
4. ตรวจว่าชุดสุดท้ายยังให้ **economic gap** (Take vs Skip) ดีอยู่หรือไม่

### 6. ข้อควรระวัง

- อย่าใช้ `model.feature_importances_` จากต้นไม้ที่เทรนด้วย random split ธรรมดา
- อย่าคัด features หลายรอบบนชุดทดสอบเดียวกันโดยไม่มีกระบวนการป้องกัน overfitting
- หลังคัด features เสร็จแล้วควร **freeze** ชุดนั้น แล้วค่อยประเมินโมเดลรอบสุดท้ายด้วย CPCV อีกครั้ง

### 7. สรุป

การทดสอบ Feature Importance ที่ถูกต้องสำหรับ Meta-Model ต้อง:

1. ใช้ข้อมูลเฉพาะจุดที่ Primary Signal เกิด  
2. รักษาลำดับเวลา  
3. ใช้ Purging (และ ideally CPCV paths)  
4. วัดจากผลกระทบต่อ performance จริงเมื่อ feature ถูกทำลายหรือถูกเอาออก  

วิธี **Purged Permutation Importance** ด้านบนเป็นจุดเริ่มต้นที่ดีและเข้ากับโครงสร้าง Platform ของคุณโดยตรง

---

**Purged LOFO Importance**  
**(Leave-One-Feature-Out with Purging / CPCV)**

LOFO Importance วัดความสำคัญของ feature โดยการ **เอาออกทีละตัว** แล้วดูว่า performance ของโมเดลแย่ลงแค่ไหน  
เมื่อทำภายใต้เงื่อนไข **Purged / CPCV** จะได้ความสำคัญที่น่าเชื่อถือสำหรับข้อมูลการเงินมากกว่าระบบ ordinary

---

### 1. แนวคิดหลัก

สำหรับแต่ละ feature \(f\):

1. เทรนโมเดลด้วย **ชุด features ครบ**
2. เทรนโมเดลด้วย **ชุดเดิมแต่ตัด \(f\) ออก**
3. เปรียบเทียบ performance บน test set ที่ถูก purge แล้ว
4. ความสำคัญของ \(f\) = ผลต่างของ performance

\[
\text{Importance}(f) = \text{Score}_{\text{full}} - \text{Score}_{\text{without } f}
\]

ถ้าตัด feature ออกแล้วผลแย่ลงมาก → feature นั้นสำคัญ  
ถ้าตัดออกแล้วผลดีขึ้นหรือไม่เปลี่ยน → feature นั้นไม่มีประโยชน์หรือเป็น noise

---

### 2. ทำไมต้องเป็นแบบ Purged

- ป้องกัน label leakage  
- รักษาลำดับเวลา  
- วัดความสำคัญข้ามหลายช่วงตลาด (เมื่อใช้ร่วมกับ combinatorial paths)  
- ลดโอกาสที่ feature จะดูสำคัญแค่เพราะ overfit ช่วงใดช่วงหนึ่ง

---

### 3. ขั้นตอนแบบละเอียด

1. สร้าง Meta-Dataset (เฉพาะวันที่ Primary Signal เกิด)
2. แบ่งเวลาเป็น \(N\) กลุ่ม และสร้าง combinatorial paths
3. ในแต่ละ path:
   - ทำ purging ตาม label horizon
   - เทรนโมเดลชุดเต็ม → วัด score
   - เทรนโมเดลโดยตัดทีละ feature → วัด score
   - บันทึกผลต่าง
4. เฉลี่ย importance ข้ามทุก paths

---

### 4. โค้ดตัวอย่าง (Purged LOFO)

```python
"""
research/lofo_purged.py
Purged Leave-One-Feature-Out Importance
"""

import numpy as np
import pandas as pd
from sklearn.linear_model import LogisticRegression
from sklearn.preprocessing import StandardScaler
from sklearn.metrics import roc_auc_score, accuracy_score

from research.advanced_features import build_advanced_panel
from research.cpcv import cpcv_splits, CORE_FEATS


def purged_lofo_importance(
    n_groups: int = 6,
    n_test_groups: int = 2,
    hold: int = 10,
    score: str = "auc",          # "auc" หรือ "hit"
):
    panel = build_advanced_panel(hold=hold)
    feats = [f for f in CORE_FEATS if f in panel.columns]
    panel = panel.dropna(subset=feats + ["y"]).copy()
    dates = sorted(panel["date"].unique())

    records = []

    for tr_dates, te_dates in cpcv_splits(dates, n_groups, n_test_groups, purge=hold):
        tr = panel[panel.date.isin(tr_dates)]
        te = panel[panel.date.isin(te_dates)]
        if len(tr) < 80 or len(te) < 20:
            continue

        y_tr, y_te = tr["y"].values, te["y"].values

        def fit_score(feature_list):
            if len(feature_list) == 0:
                return np.nan
            sc = StandardScaler().fit(tr[feature_list])
            X_tr = sc.transform(tr[feature_list])
            X_te = sc.transform(te[feature_list])
            m = LogisticRegression(max_iter=2000, C=0.5, class_weight="balanced")
            m.fit(X_tr, y_tr)
            p = m.predict_proba(X_te)[:, 1]
            if score == "auc":
                try:
                    return roc_auc_score(y_te, p)
                except Exception:
                    return np.nan
            else:
                return accuracy_score(y_te, (p >= 0.5).astype(int))

        # Full model
        full_score = fit_score(feats)

        # Leave one feature out
        for f in feats:
            reduced = [x for x in feats if x != f]
            reduced_score = fit_score(reduced)
            drop = full_score - reduced_score          # ยิ่งมาก = ยิ่งสำคัญ
            records.append({
                "feature": f,
                "full_score": full_score,
                "reduced_score": reduced_score,
                "importance": drop,
                "n_te": len(te),
            })

    df = pd.DataFrame(records)
    if df.empty:
        print("ข้อมูลไม่เพียงพอ")
        return df

    summary = (
        df.groupby("feature")["importance"]
        .agg(
            mean_importance="mean",
            std_importance="std",
            n_paths="count",
        )
        .sort_values("mean_importance", ascending=False)
        .round(4)
    )

    print("=" * 64)
    print(f"PURGED LOFO IMPORTANCE  (score = {score})")
    print("ค่าสูง = เมื่อตัด feature นี้จากโมเดล แล้วผลแย่ลงชัด")
    print("=" * 64)
    print(summary)
    print("=" * 64)
    return summary


if __name__ == "__main__":
    purged_lofo_importance(score="auc")
```

---

### 5. วิธีอ่านผล LOFO

| ค่า mean_importance | ความหมาย |
|---------------------|---------|
| บวกสูง | Feature สำคัญมาก (ตัดแล้วโมเดลแย่ลงชัด) |
| ใกล้ 0 | Feature แทบไม่มีประโยชน์ |
| ติดลบ | ตัดออกแล้วโมเดลดีขึ้น → น่าจะเป็น noise หรือ redundant |

ดูคู่กับ `std_importance`:
- สำคัญและเสถียร → เก็บ
- สำคัญแต่ std สูง → ใช้ด้วยความระวัง
- ไม่สำคัญสม่ำเสมอ → ตัดทิ้ง

---

### 6. เปรียบเทียบกับ Purged Permutation Importance

| มิติ | Purged Permutation | Purged LOFO |
|------|--------------------|-------------|
| วิธีรบกวน feature | สุ่มสลายค่าใน test set | ตัดออกจากโมเดลเลย |
| จับ interaction | ปานกลาง | ดีกว่า (เพราะเทรนใหม่) |
| ค่าใช้จ่ายในการคำนวณ | ต่ำกว่า | สูงกว่า |
| ความเข้มงวด | สูง | สูงมาก |
| เหมาะกับ | สำรวจเบื้องต้น | ยืนยันชุด features สุดท้าย |

แนวทางที่ดี:
1. ใช้ Permutation Importance กรองเบื้องต้น  
2. ใช้ LOFO ยืนยันชุดที่เหลือ

---

### 7. ข้อควรปฏิบัติ

- ใช้ label horizon เดียวกับที่โมเดลจะใช้จริง  
- ทำบน combinatorial paths ไม่ใช่แค่ split เดียว  
- หลังคัด features เสร็จแล้ว ต้องรัน CPCV ประเมินโมเดลชุดสุดท้ายอีกครั้ง  
- อย่าตัด/เพิ่ม features วนไปมาหลังเห็นผลลัพธ์สุดท้าย (ป้องกัน selection bias)

---

### 8. สรุป

**Purged LOFO Importance** =  
วัดว่า feature แต่ละตัว “จำเป็น” แค่ไหน โดยการเอาออกทีละตัว และประเมินภายใต้เงื่อนไขที่ไม่มี leakage

เป็นหนึ่งในวิธีที่น่าเชื่อถือที่สุดสำหรับการคัด features ของ Meta-Model ในระบบการเงิน

ต้องการให้ผมช่วยต่อไหมครับ?
- รวม Permutation + LOFO เป็น pipeline คัด features อัตโนมัติ  
- เพิ่มการวัด economic importance (ผลกระทบต่อ Take–Skip gap)  
- หรือออกแบบเกณฑ์ตัด feature แบบ rule-based จากผลลัพธ์ LOFO
